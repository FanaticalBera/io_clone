# PRD — 육각형 영토 점령 멀티 게임

버전: 0.5 / 작성일: 2026-09-30 / 수정일: 2026-10-01 / 상태: 영토와 꼬리 연결 단절·전장 축소·미세 조작 안정화 반영

2026-10-01 사용자 요청으로 고립 영토 제거·외곽 벽 충돌 탈락·처치/사망 피드백 및 Classic/Hold 모드를 반영했습니다. 4분·거점 총점 규칙은 현재 모드에서 사용하지 않습니다. 작성 당시의 계획 전용 문장은 원래 문서 목적을 설명하며, 이후 사용자의 구현·수정 요청을 제한하지 않습니다.

## 1. 문서 목적과 결정 상태

이 문서는 Six.io의 기본 플레이에서 출발한 새로운 육각형 영토 점령 게임의 제품 요구사항을 정의한다. Codex가 이 문서를 바탕으로 TECH_SPEC.md와 TASKS.md를 작성하고, 이후 단계별로 구현할 수 있도록 범위·게임 규칙·사용자 흐름·완료 기준을 명시한다.

현재 요청은 PRD 작성이다. 이 문서 자체는 코드 구현이나 서비스 배포를 시작하라는 지시가 아니다.

| 구분 | 내용 |
|---|---|
| 사용자 요구 | 육각형 땅따먹기, 실제 온라인 멀티플레이, 부족한 인원을 채우는 컴퓨터 상대, 도전적인 플레이 |
| 제안된 개발 방향 | TypeScript + Phaser 게임 클라이언트, Node.js + Socket.IO 서버, 추후 Capacitor 안드로이드 앱 |
| 현재 구현 범위 | 개인전, 사람·봇 혼합 8슬롯, Classic/Hold, 재등장, 공개 대전·친구 초대방·봇 연습 |
| 아직 확정되지 않은 항목 | 게임 이름, 세부 수치, 최종 아트·사운드, 운영 서버·배포 방식, 안드로이드 출시 시점 |

아래 규칙은 개발자가 임의로 결정하지 않아도 되도록 작성한 초기 기본안이다. 사용자 검토와 플레이 테스트로 변경할 수 있다. 특히 수치는 확정된 밸런스로 취급하지 않는다.

## 2. 제품 개요

### 2.1 한 문장 설명

자기 땅 밖에 선을 그어 영토를 넓히고 상대의 선을 끊으며, 완전 점령 또는 영토 우위 유지로 승리하는 멀티 게임.

### 2.2 해결하려는 문제

- 사람이 적어도 대기만 하다 끝나지 않고 봇과 즉시 플레이할 수 있어야 한다.
- 친구와 링크 또는 방 코드로 같은 판에 쉽게 참가할 수 있어야 한다.
- 영토 우위를 빼앗거나 상대의 유지 조건을 끊는 견제가 의미 있어야 한다.
- 한 번 죽은 뒤 장시간 관전해야 하는 부담을 줄여야 한다.
- PC와 휴대폰에서 같은 기본 규칙으로 플레이할 수 있어야 한다.

### 2.3 주요 사용자

1. 혼자 접속해 짧게 플레이하는 사용자.
2. 친구 1~7명과 같은 방에서 경쟁하는 사용자.
3. 봇 연습으로 규칙과 조작을 익히는 사용자.

### 2.4 제품 원칙

- 기본 조작과 규칙은 짧은 설명으로 이해할 수 있게 한다.
- 넓게 점령할수록 오래 노출되는 원래의 위험·보상 관계를 유지한다.
- 봇은 사람과 같은 규칙을 사용하고 봇임을 표시한다.
- 게임 결과는 서버가 판정하며, 화면의 연출은 그 결과를 따른다.
- 원작의 이름·이미지·사운드·캐릭터·코드는 가져오지 않는다. 자체 이름과 자산을 사용한다.

## 3. MVP 범위와 이후 범위

| 우선순위 | 포함 기능 |
|---|---|
| MVP 필수 | 육각형 맵, 이동선, 영토 점령, 선 절단, 재등장, 모드·점유율·처치·순위 |
| MVP 필수 | 실제 온라인 대전, 공개 방 자동 입장, 친구 초대방, 봇 인원 보충 |
| MVP 필수 | Classic/Hold 승리 조건, 기본 봇 성격, 서버 없이 진행하는 봇 연습 |
| MVP 필수 | PC 키보드·마우스 조작, 모바일 터치 조작, 기본 튜토리얼·상태 안내 |
| 후속 업데이트 | 대시 능력, 도전 모드, 일일 고정 조건 도전, 외형 보상 |
| 후속 업데이트 | 거점 활성 상태 변경, 맵 변형, 봇 난이도 확대, 안드로이드 패키징·기기 QA |
| 초기 범위 제외 | 계정·로그인, 영구 랭킹, 채팅, 팀전, 친구 목록, 결제·광고, 능력치 성장, 학습형 AI |
| 초기 범위 제외 | 관전 전용 입장, 중도 참가자의 즉시 전장 투입, 대규모 분산 서버, iOS 앱 |

MVP의 멀티는 실제로 서로 다른 클라이언트가 동일한 서버의 동일한 판에 참여하는 것을 의미한다. 각 기기에서 별도로 실행되는 봇 판을 멀티처럼 표시해서는 안 된다.

## 5. 게임 규칙

### 5.1 용어

| 용어 | 정의 |
|---|---|
| 영토 | 특정 참가자가 소유한 육각형 칸들의 집합 |
| 캐릭터 | 참가자가 조작하는 이동 개체 |
| 이동선 / 꼬리 | 자기 영토 밖에서 이동하며 남긴 선 전체. 캐릭터 바로 뒤의 일부만을 뜻하지 않는다. |
| 복귀 | 이동선을 남긴 상태에서 자기 소유 칸에 다시 진입하는 것 |
| 점령 | 복귀가 유효하게 완료되었을 때 이동선과 그 선이 둘러싼 칸의 소유권을 변경하는 것 |
| 제거 | 다른 참가자의 노출된 이동선을 접촉하여 그 참가자를 탈락시키는 것 |

### 5.2 이동과 조작

- 캐릭터는 선택한 방향으로 일정 속도로 계속 이동한다. 정지 명령은 MVP에 없다.
- PC는 WASD 또는 방향키를 기본으로 제공하고, 마우스로 방향을 지정하는 조작도 제공한다. 방향 키를 누르는 동안에는 키보드가 우선하며 키를 놓은 뒤 새 유효 마우스 입력으로 전환한다.
- 모바일은 환경설정에서 가상 조이스틱(기본) 또는 화면 드래그를 선택한다. 화면 드래그는 PC 마우스와 같은 캐릭터→포인터 위치 방식으로 목표를 지정하며, 누른 위치부터 방향 지정이 시작된다. 손을 떼면 마지막 방향을 유지한다. 버튼·정보 카드에서는 전장 드래그를 시작하지 않는다.
- 작은 움직임에 방향이 크게 바뀌지 않도록 조이스틱 중앙 반경 25%, 화면 포인터의 캐릭터 주변 18 CSS px와 2도 미만 목표 변화를 무시한다. 손가락 이동 구간이나 최초 터치점을 목표의 기준으로 삼지 않는다. 같은 쪽에서 손가락을 되돌리면 그쪽 목표가 유지되고 캐릭터 반대쪽을 가리키면 반대 목표를 받는다. 화면 좌표와 캐릭터 위치는 같은 렌더 프레임을 사용한다. 조이스틱의 각도 필터도 2도다. 실제 진행 방향은 9rad/s로 회전한다. 손을 떼면 마지막 목표까지 회전한 뒤 계속 전진한다. 반대 입력에도 즉시 반전하지 않는다.
- 전장 표시 확대는 PC/가로 화면 0.50, 폭 600px 미만 화면 0.45를 사용한다. 기본 육각 칸 폭은 약 28/25 CSS px다. 이는 표현 변경이며 판정 크기·맵·이동 속도를 바꾸지 않는다. 이름 라벨의 읽기 크기를 보완한다. S24 세로 HUD 전면 수정은 계속 후순위다.
- 메뉴·로비·경기·결과에서 환경설정을 열 수 있고 선택한 조작 방식과 처치 진동 여부를 브라우저에 저장한다. 설정 중 연습은 정지, 온라인은 계속 진행하며 설정 창 입력은 이동 방향에 반영하지 않는다.
- 처치 진동은 기본 켜짐이며 지원 모바일 브라우저에서 새로 확정된 자기 처치에만 반응한다. 자기 사망·벽 충돌·과거 사건 재수신에는 진동하지 않는다. 켜기/끄기와 진동 테스트를 제공하고 미지원 환경에서는 테스트를 비활성화한다. 실제 기기 진동 여부는 별도 검증 항목이다.
- Classic 100% 승리 직후 기존 결과 팝업으로 확정 승자와 최종 기록을 표시한다. 이번에는 추가 모드를 만들거나 승리 애니메이션을 추가하지 않는다.
- 캐릭터 중심이 맵 외곽 벽을 통과하려는 순간 탈락한다. 외곽 칸에 있는 것만으로 죽지는 않으며 충돌 전에 안쪽으로 방향을 바꾸면 생존한다. 재등장 보호도 벽 충돌은 막지 않는다.
- 경계와 캐릭터 간 충돌 크기, 이동 보간, 입력 정규화는 TECH_SPEC에서 구체화한다.
- 초기 등장 방향과 위치는 시작 직후 경계나 상대 선에 충돌하지 않도록 배치한다.

### 5.3 영토 점령

1. 자기 영토 안에서는 이동선이 생기지 않는다.
2. 자기 영토를 벗어나면 지나간 칸에 이동선이 생긴다.
3. 자기 영토의 어느 칸으로든 복귀하면 이동 경로가 마감된다.
4. 마감된 이동선에 해당하는 칸과, 자기 영토·이동선으로 완전히 둘러싸인 칸을 점령한다.
5. 마감 전에는 이동선이 지나간 칸의 기존 소유권이 바뀌지 않는다.

추가 규칙:

- 빈 칸과 상대 영토 모두 점령할 수 있다.
- 노출된 선이 연결돼 있던 상대 영토를 점령하거나 연결 다리를 빼앗아 그 영토가 고립 정리로 사라졌다면, 자기 영토와의 연결을 잃은 상대는 절단 탈락한다. 다른 곳의 남은 영토만으로는 살아남지 못한다. 점령 이후에도 선이 남은 본영토에 연결돼 있다면 생존한다.
- 실제 점령한 경로 또는 내부 영역에 상대의 노출된 선이 포함되면 그 상대를 절단 탈락시키고 점령자에게 처치 횟수를 부여한다. 상대 본체·남은 영토가 바깥에 있어도 적용한다. 점령 밖에 있고 자기 영토 연결이 유지된 선이나 마감된 선에는 적용하지 않는다.
- 단순히 선만 스쳐 지나가서는 내부 영역이 자동으로 점령되지 않는다. 복귀가 필요하다.
- 외부와 연결된 열린 영역은 점령하지 않는다. 맵 경계만으로 열린 경로를 자동 폐쇄하지 않는다.
- 기존 소유 칸을 다시 점령해도 중복 칸이나 추가 점수를 만들지 않는다.
- 자기 이동선을 교차해도 사망하지 않는다. 교차만으로 점령이 완료되지는 않으며 복귀 시점에 판정한다.
- 여러 폐쇄 영역이 생기면 규칙에 따라 실제로 둘러싸인 영역만 점령한다.
- 다른 참가자가 서 있는 칸을 점령한 사실만으로는 즉시 사망하지 않는다. 노출된 선이 덮였거나 그 선의 자기 영토 연결이 끊어졌다면 절단 규칙을 적용한다.
- 다른 참가자의 영토가 완전히 사라지면 그 참가자는 탈락한다. 영토 소멸만으로 제거 횟수를 특정 공격자에게 부여하지 않는다.
- 점령으로 영토 연결이 끊기면 가장 큰 6방향 연결 영역만 본영토로 남기고 다른 고립 영역은 즉시 중립화한다. 크기가 같으면 가장 낮은 cellId가 포함된 영역을 유지한다. 캐릭터 위치와 관계없이 모든 참가자에게 같은 기준을 적용한다.
- 제거된 영역은 영토 칸 수와 점유율에 즉시 반영한다. 거점 관련 데이터는 향후 모드용으로 보존하되 현재 점수는 지급하지 않는다.
- 상대가 현재 서 있던 소유 칸을 빼앗으면, 살아 있는 상대는 그 위치부터 영토 밖 이동선을 남기는 상태로 전환한다.

점령 알고리즘과 육각형 인접 관계는 TECH_SPEC에서 정의하되, 위 결과를 만족해야 한다.

### 5.4 선 접촉과 판정 일관성

- 살아 있는 참가자가 다른 참가자의 노출된 이동선 어느 부분이든 건드리면 선의 소유자가 탈락한다.
- 새 점령 영역으로 상대의 노출된 선을 덮거나 연결 영토를 제거하는 경우에도 같은 선 절단 규칙과 처치·사망 효과를 적용한다. 한 번에 여러 선을 절단할 수 있으나 참가자당 사망과 처치 크레딧은 한 번만 적용한다.
- 상대 캐릭터 본체에 닿는 것만으로는 탈락하지 않는다.
- 자기 선은 절단할 수 없다.
- 탈락자의 진행 중 이동선은 즉시 사라지고, 기존 영토는 중립 칸으로 돌아간다.
- 이동선 절단을 유발한 참가자의 제거 횟수를 1회 증가시킨다.
- 같은 판정 구간에서 서로의 선을 절단했다면 양쪽 모두 탈락할 수 있다.
- 접촉이 자기 영토 복귀보다 먼저 발생했다면 탈락, 복귀가 먼저 완료됐다면 이미 마감된 선을 뒤늦게 절단할 수 없다.
- 접촉과 복귀가 정확히 같은 판정 시점이면 선 절단을 우선한다.
- 여러 참가자가 동시에 같은 칸을 점령하는 등 나머지 동시 사건은 서버가 일관된 순서를 정한다. 상세 순서와 동점 처리 알고리즘은 TECH_SPEC에 명시한다.
- 클라이언트의 프레임 속도, 패킷 수신 순서, 화면상의 예측만으로 승패를 결정하지 않는다.

### 5.5 탈락과 재등장

- 탈락 원인과 재등장까지 남은 시간을 화면에 표시한다.
- 선 절단·영토 소멸·외곽 벽 충돌을 탈락 원인으로 구분한다. 벽 충돌은 상대 제거 횟수를 올리지 않는다.
- 처치 횟수는 유지하고 영토는 초기화한다. Classic/Hold의 거점 점수는 지급하지 않는다.
- 재등장 시 작은 시작 영토를 새로 부여한다.
- 재등장 위치는 기존 참가자의 영토를 빼앗거나 진행 중인 이동선을 지우지 않는다. 거점 위에 배치하지 않는다.
- 기존 캐릭터·노출된 선과 충분히 떨어진 중립 영역을 우선한다. 안전 거리와 공간 부족 시 대기·재시도 정책은 TECH_SPEC에 명시한다.
- 안전한 위치가 없으면 대기 시간을 늘리고 화면에 안내한다. 위험한 곳에 억지로 등장시키지 않는다.
- 재등장 보호는 시작 영토 안에 있는 동안 최대 2초만 적용한다. 밖으로 나가면 즉시 종료한다.
- 보호 중에는 상대를 제거하거나 거점을 점령할 수 없다. 보호 종료 시 일반 규칙으로 돌아간다.
- 보호가 화면에 구별되게 표시되어야 한다.

### 5.6 거점 — 기존 코드 보존

기존 고정 거점 위치·점수 지급 코드는 향후 별도 모드에서 재사용할 수 있도록 보존한다. Classic/Hold에서는 거점을 표시하거나 점수를 지급하지 않으며 승패·순위에도 영향을 주지 않는다. 세 번째 모드는 이번 범위에 추가하지 않는다.

### 5.7 게임 모드와 승리

- 안정적인 mode id는 `classic`, `hold`이며 초기 모드는 Classic이다.
- Classic: 시간 제한 없이 전체 플레이 가능 칸 100%를 소유한 생존자가 즉시 승리한다. 80%/95% 보정, 자동 맵 축소, 추가 유지 시간은 없다.
- Hold: 기본 목표 점유율 50%, 연속 유지 10초. 목표치 이상이면 카운트다운을 시작한다. 목표치 아래로 내려가거나 사망하면 즉시 취소한다. 재달성하면 전체 유지 시간을 처음부터 계산한다. 목표·기간은 모드 설정으로 관리한다.
- 점유율의 분모는 중립·상대 영토를 포함한 전체 플레이 가능 칸 수다. 승리 판정에는 실제 칸 수를 사용하며 HUD 표시 반올림으로 승리하지 않는다.
- 같은 시간의 절단·벽 충돌·점령·고립 영토 정리·영토 소멸을 모두 처리한 뒤 승리를 판정한다. 유지 조건이 틱 중간에 깨졌다가 회복돼도 다시 시작한다.
- 여러 참가자가 Hold 조건을 만족하면 각 유지 시간을 추적한다. 가장 먼저 연속 유지 기간을 완료한 생존자가 승리한다. 완료 시각도 같으면 해당 판의 시드 우선순위로 확정한다.
- 온라인은 서버가 즉시 한 번만 승리를 확정하고 종료한다. 종료 이후 입력·중복 이벤트는 결과를 바꾸지 않는다. 봇 연습은 같은 코어 규칙을 로컬에서 실행한다.
- HUD·순위·결과는 점유율, 영토 칸 수, 처치 수를 표시한다. 순위는 영토 내림차순, 처치 내림차순이며 같으면 1,1,3 공동 순위다. 결과의 확정 승자는 1위로 표시한다. 이탈자는 LEFT이며 우승 대상에서 제외한다.

## 6. 플레이 모드와 방 운영

### 6.1 공개 대전

- 첫 화면에서 모드를 선택한 뒤 공개 대전을 누른다. 선택한 모드의 대기 방만 매칭하며 없으면 같은 모드의 방을 만든다.
- 방 종류(PUBLIC/FRIEND)와 게임 모드(classic/hold)는 별도로 관리한다.
- 첫 사람 입장 후 기본 5초 이내에 봇으로 빈 슬롯을 채워 라운드를 시작한다.
- 이미 진행 중인 방에 늦게 들어간 사람은 다음 라운드를 기다리게 하지 않고, 들어갈 수 있는 대기 방 또는 새 방에 배정한다.
- 사람·봇 구성은 라운드 시작 시 확정한다. 진행 중 봇을 갑자기 사람으로 바꾸지 않는다.
- 결과 화면에서 다음 판 참가 또는 나가기를 선택한다. 온라인 방은 10초 후 남아 있는 사람들과 다음 판을 시작한다.

### 6.2 친구 초대방

- 방 만들기, 초대 링크 복사, 방 코드 입력을 제공한다.
- 메인 화면에서 선택한 모드로 생성한다. 로비에는 모드와 규칙을 읽기 전용으로 표시하고 생성 이후 변경하지 않는다. 코드로 입장한 사람도 방의 모드를 확인한다.
- 방의 사람 참가 한도는 8명이고, 부족한 슬롯은 라운드 시작 시 봇으로 채운다.
- 최소 한 사람이 있으면 방장이 시작할 수 있다.
- 진행 중 초대 링크로 들어온 사람은 대기 화면에서 현재 모드·경기 진행 중 안내와 다음 판 참가 상태를 확인한다. MVP에서는 현재 전장 관전 화면을 제공하지 않는다.
- 다음 라운드 시작 시 대기 중 사람을 우선 배치하고, 빈 슬롯만 봇으로 채운다. 대기 인원도 사람 한도에 포함한다.
- 방이 가득 차면 입장 실패 이유를 표시한다.
- 방장이 나가면 남은 사람 중 먼저 입장한 사람에게 방장 권한을 넘긴다. 이미 시작된 게임을 중단하지 않는다.
- 복잡한 방 규칙 편집은 MVP에 포함하지 않는다.

### 6.3 봇 연습

- 사람 1명 + 봇 7명으로 서버 연결 없이 한 판을 진행할 수 있어야 한다.
- 선택한 모드의 온라인과 같은 이동·점령·절단·탈락·재등장·승리 규칙을 사용한다.
- 온라인 서버에 연결할 수 없을 때 연습 모드로 이동하는 선택지를 제공한다.
- 초기 파일 다운로드까지 네트워크 없이 보장하는 기능은 MVP 범위가 아니다.
- 결과 화면에서 사용자가 재시작을 선택한다. 연습 모드를 자동으로 다음 판에 넣지 않는다.

### 6.4 연결 끊김과 방 정리

- 온라인 서버에는 사람이 보는 화면과 별개로 경기 진행 상태가 존재한다.
- 연결이 끊긴 사람은 최대 10초 동안 같은 참가자로 복구할 수 있다. 복구 과정에서 추가 영토·생명·점수를 얻지 않는다.
- 유예 중 캐릭터는 규칙 기반 자동 조작으로 자기 영토 복귀를 시도하며, 정상적으로 공격받거나 탈락할 수 있다. 연결 끊김을 무적·일시정지 수단으로 만들지 않는다.
- 유예가 끝나면 참가자는 이탈 처리되고 진행 중 선과 영토를 중립화한다. 해당 슬롯에는 새 봇을 작은 영토로 등장시키며, 이탈자의 점수·영토를 물려주지 않는다.
- 사람 이탈 후에도 남아 있는 사람의 라운드는 계속된다.
- 방에 사람이 한 명도 남지 않으면 60초 이내에 경기·타이머·네트워크 자원을 정리한다.
- 서버가 중단된 경기의 영속 복구는 MVP에서 제공하지 않는다. 사용자에게 종료 이유와 재입장 선택지를 제공한다.

## 7. 봇 요구사항

### 7.1 구현 범위

MVP는 규칙 기반 봇을 사용한다. 학습 모델, 외부 AI API, 파인튜닝은 필요하지 않다.

| 성격 | 행동 경향 |
|---|---|
| 확장형 | 빈 영역을 찾고 비교적 큰 경로로 점령 |
| 공격형 | 접근 가능한 상대 이동선을 노리되 복귀 가능성 고려 |
| 수비형 | 짧은 점령과 빠른 복귀를 선호 |
| 거점형(기존 성격 id 보존) | Classic/Hold에서는 일반 확장 경로 사용; 활성 거점 모드용 계획 코드 보존 |

- 기본 난이도 1종에 네 성격을 혼합한다. 난이도 선택 UI는 후속 범위다.
- 봇은 사람과 같은 이동 속도·충돌·영토·재등장·점수 규칙을 사용한다.
- 봇의 방향 판단은 일정 간격으로 갱신하여 즉각적인 완벽 대응을 피한다.
- 상대 입력이나 아직 전달되지 않은 미래 행동을 알아내는 방식으로 행동하지 않는다.
- 봇은 영역 밖으로 나갔다가 복귀해 실제 점령을 수행할 수 있어야 한다.
- 한 상태에 계속 머무르거나 맵 경계에서 무한히 방향만 바꾸지 않도록 한다.
- 온라인에서는 서버가 봇을 조작한다. 클라이언트마다 별도의 봇을 계산하지 않는다.
- 이름과 순위표에 BOT 표기를 사용한다. 사람이 없는 대전을 사람과 대전 중인 것처럼 표시하지 않는다.

## 8. 화면과 사용자 흐름

### 8.1 필수 화면

메인 메뉴 안에서 CLASSIC ↔ HOLD를 좌우 버튼·마우스 드래그·모바일 스와이프로 선택한다. Classic은 `완전 점령 / 맵 전체를 자신의 영토로 만들면 승리`, Hold는 `영토 유지 / 목표 점유율을 일정 시간 유지하면 승리`를 표시한다. 우측 정보는 `100% 점령` 또는 `50% · 10초 유지`, `최대 8명`, `PC · 모바일`이다. 크림색·민트·보라·굵은 테두리·카드 디자인은 유지한다.

Hold 경기 중 서버가 확정한 유지 참가자의 이름과 남은 초를 기존 중앙 타이머 영역에 표시한다. 조건이 깨지면 표시를 즉시 취소한다. S24 세로 HUD 전체 겹침 문제는 사용자 요청에 따라 후속 작업으로 유예한다.

| 화면 | 필수 요소 |
|---|---|
| 시작 | 닉네임, 공개 대전, 친구 방 만들기·입장, 봇 연습, 조작 설명 |
| 친구 방 대기 | 방 코드·초대 링크, 사람 목록·인원, 방장 표시, 시작·나가기 |
| 연결·입장 상태 | 연결 중, 오류, 재시도, 연습 모드 선택 |
| 경기 | 맵, 캐릭터·이동선·영토, 모드 목표·Hold 유지 상태, 점유율·처치·순위, 사람·봇 수 |
| 탈락 | 원인, 재등장 카운트다운 또는 안전 위치 대기 안내 |
| 결과 | 모드·확정 승자·점유율·영토 칸·처치/사망·순위, 다음 판 또는 재시작, 나가기 |

### 8.2 첫 사용자 안내

첫 플레이 전에 아래 세 규칙을 간단한 그림 또는 짧은 시연으로 안내한다. 안내는 건너뛸 수 있고 다시 열 수 있어야 한다.

1. 밖으로 나가 선을 그리고 자기 땅으로 돌아오면 점령.
2. 노출된 선 어느 부분이든 상대가 건드리면 탈락.
3. 선택한 모드의 목표를 달성하면 승리: Classic은 100% 점령, Hold는 목표 점유율 연속 유지.

### 8.3 화면 품질과 입력

- 캐릭터 주변을 따라가는 카메라와 전체 영토·자기 위치를 확인할 수 있는 간단한 미니맵을 제공한다.
- 자기 선, 자기 영토, 상대 영토는 즉시 구별되어야 한다.
- 색상 외에도 이름·테두리·기호를 사용하여 소유자를 구분한다.
- 모바일 HUD와 가상 조이스틱은 중요한 상태나 주 조작 영역을 과도하게 가리지 않는다.
- 가로 화면을 기준으로 디자인하되 세로 화면에서도 조작과 필수 HUD가 잘리지 않도록 한다. 가로 전환 안내는 가능하지만 강제하지 않는다.
- 모바일 플레이 중 스크롤·텍스트 선택이 조작을 방해하지 않게 한다.
- 닉네임은 공백 정리 후 1~16자로 제한하고, HTML·스크립트로 해석하지 않는다. 중복 닉네임도 서로 다른 참가자로 구분한다.
- 기본 시각 피드백을 우선한다. 사운드가 없어도 점령·탈락·거점 탈환을 이해할 수 있어야 한다.
- 처치·사망은 확정된 사건 위치에서 파편·충격파로 표시한다. 자기 처치에는 짧은 민트색 화면 반응·처치 안내, 자기 사망에는 붉은 화면 반응·원인 안내를 제공한다. 중복 상태 수신·재연결로 과거 효과를 다시 재생하지 않는다.

## 9. 멀티플레이·성능·운영 요구사항

### 9.1 판정과 통신

- 서버가 위치, 이동선, 점령, 탈락, 점수와 시간의 최종 권한을 가진다.
- 클라이언트는 방향 등 허용된 입력을 보내며 점수·영토 소유권을 직접 확정하지 않는다.
- 잘못된 방향값, 과도한 입력 빈도, 다른 방·다른 참가자의 상태 변경 요청은 경기 상태를 훼손하지 못해야 한다.
- 화면에서 내 이동을 미리 보여주고 서버 상태와 맞추는 처리를 검토한다. 상대 움직임은 튀지 않도록 표현한다.
- 방 간 맵·참가자·점수·이벤트가 섞이지 않아야 한다.
- 운영 서버는 실시간 연결을 지원해야 한다. 정적 웹 호스팅만으로 멀티가 완성된 것으로 간주하지 않는다.
- 서버 주기, 상태 전달 방식, 지연 보정, 입력 검증, 방 코드 정책은 TECH_SPEC에서 정한다.

### 9.2 초기 검증 목표

아래는 측정할 목표이며, 검증 결과 없이 성능을 보장했다고 보고하지 않는다. 구현 시작 시 시험 기기·브라우저·맵 규모를 TECH_SPEC에 기록한다.

| 항목 | 초기 목표·검증 조건 |
|---|---|
| PC 렌더링 | 합의한 시험 PC에서 8참가자·기본 맵 기준 평균 60 FPS 목표 |
| 모바일 렌더링 | 합의한 시험 안드로이드 기기에서 평균 30 FPS 이상 목표 |
| 정상 멀티 | 서로 다른 브라우저 세션 두 개 이상이 같은 맵·결과를 확인 |
| 최대 인원 | 8개 사람 연결로 한 라운드 완료; 별도로 사람·봇 혼합 확인 |
| 연속 플레이 | 최소 3개 연속 라운드 동안 오류·참가자·타이머 누적 없음 |
| 방 격리 | 두 방이 동시에 진행되어도 서로의 상태·결과가 섞이지 않음 |
| 연결 복구 | 일시 끊김과 재연결 후 상태·점수가 중복 생성되지 않음 |
| 지연 | 100ms 수준 RTT에서 조작·복귀·절단·결과를 점검하고 문제 기록 |
| 시작 경험 | 실행 가능한 파일 로드 후 공개 대전 대기 기본 5초 이내 |

최초 접속 파일 로딩 속도와 총 동시 방 수 목표는 배포 환경 선정 후 별도로 정한다. 지연으로 화면상의 접촉과 서버 판정이 다를 수 있으므로, 최종 판정 기준과 보정의 한계를 기술 설계에 명시한다.

### 9.3 운영과 저장

- MVP의 방과 경기 상태는 일시적이다. 영구 데이터베이스가 필수는 아니다.
- 로컬 개발 환경에서 서버와 클라이언트를 실행하는 명령과 친구 테스트 방법을 README에 제공한다.
- 외부 배포를 수행하는 단계에서는 HTTP 자산과 실시간 연결의 주소·HTTPS/WSS 구성을 검증한다.
- 방 생성·종료, 접속·이탈, 비정상 입력, 서버 오류를 확인할 최소 로그를 제공한다.
- 접속 유예에 필요한 식별 정보를 닉네임과 분리한다. 재연결 식별 정보를 일반 로그에 노출하지 않는다.
- 공개 배포와 스토어 출시는 구현 완료와 별개의 후속 작업이다. 제공되지 않은 계정·서버·서명 정보를 임의로 가정하지 않는다.

## 11. 후속 도전 요소

아래 아이디어는 MVP 필수 기능이 아니다. 기본 게임의 재미와 온라인 안정성을 확인한 후 별도 요구사항으로 확정한다.

| 아이디어 | 플레이 목적 | 검토할 점 |
|---|---|---|
| 짧은 대시 | 절단 공격과 긴급 복귀의 타이밍 선택 | 사용 중 선의 취약성 유지, 지속시간·재사용 시간 |
| 제한시간 확장 | 90초 안에 일정 면적 확보 | 맵 규모에 따른 목표 조정 |
| 공격형 봇 생존 | 공격적인 상대 사이에서 일정 시간 생존 | 억울한 등장·초기 난이도 방지 |
| 거점 탈환 | 제한시간 안에 적의 거점 점령 | 출발 위치·적 배치의 반복 가능성 |
| 한 번에 큰 점령 | 한 번의 복귀로 많은 칸 확보 | 면적 계산과 결과 피드백 |
| 일일 같은 조건 도전 | 동일 맵·봇 조건으로 개인 기록 비교 | 고정 시드, 게임 버전, 저장·기록 검증 |
| 외형 보상 | 재도전 동기 제공 | 경쟁 능력치를 바꾸지 않는 보상 |

## 12. 개발 진행 순서와 다음 문서

| 단계 | 검토 가능한 산출물 |
|---|---|
| 1. PRD 검토 | MVP 범위, 초기 규칙·수치, 수용 기준 |
| 2. TECH_SPEC 작성 | 기술 선택 이유, 공유 게임 규칙, 점령·충돌·동시 사건, 서버·방·봇·입력·테스트 설계 |
| 3. TASKS 작성 | 독립적으로 구현·검증할 수 있는 작업, 의존 순서, 각 작업의 완료 기준 |
| 4. 기본 게임 | 이동·점령·절단·재등장 가능한 로컬 봇 판 |
| 5. 멀티 | 서로 다른 클라이언트의 동일 방 대전, 방 격리·연결 복구 |
| 6. MVP 게임성 | Classic/Hold·점유율·처치·봇 성격·결과 화면 |
| 7. QA와 배포 준비 | PC·모바일·최대 인원·연속 라운드 검증, README |
| 8. 후속 | 밸런스 조정, 도전 요소, 안드로이드 패키징 |

TECH_SPEC에는 라이브러리 버전과 운영 전제를 구현 시점에 확인하여 기록한다. 특정 버전·서버 사업자·프로젝트 구조를 PRD만으로 고정하지 않는다.

### Codex에 전달할 다음 요청

> 첨부한 PRD.md를 바탕으로 TECH_SPEC.md를 작성해라. 기술 선택에는 이유를 명시하고, 작은 규모의 개인 개발에 맞춰 과도한 엔지니어링을 피하라. 육각형 점령, 선 충돌과 동시 사건, 공유 규칙, 서버 권한, 사람·봇 혼합 방, 연결 복구, PC·모바일 입력, 검증 방법을 구체적으로 설계해라. 초기 제안 수치는 설정으로 조정할 수 있게 하고, PRD의 MVP와 후속 기능을 구분해라. 모순이나 누락이 있으면 먼저 정리하고 합리적인 기본안을 문서에 표시해라. 아직 게임 코드는 작성하거나 수정하지 마라.
