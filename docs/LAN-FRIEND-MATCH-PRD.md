## 0. v1 → v2 변경 요약

v1 이후 저장소를 직접 읽고 확인했다. 그 결과 설계의 무게중심이 바뀌었다.

| 주제 | v1 | v2 | 근거 |
| --- | --- | --- | --- |
| 엔진 분리 | 큰 작업으로 가정(2단계) | **이미 완료.** 방 관리 코드만 공통화 | `src/shared/*`는 Node 의존성 없음. `PracticeSession`이 브라우저에서 엔진·봇을 이미 실행 중 |
| 앱 래퍼 | "기존 래퍼 확인" | **신규 구축.** 가장 큰 미지수 | 저장소에 Capacitor·Cordova·`android/` 없음 |
| 방 발견 | NSD/mDNS 또는 UDP | **방코드에 방장 IP를 넣는다. 발견 단계 자체를 없앤다** | 8자리 × 32문자 = 40비트로 IPv4(32비트)와 포트·검사값을 담을 수 있음 |
| 데이터 전송 | WebRTC 우선, TCP 대체 | **네이티브 TCP 하나만 쓴다. WebRTC 제외** | signaling 서버가 따로 필요 없고, WebView의 mDNS 후보 은닉과 ICE 실패 위험이 사라짐 |
| 동기화 | 초기 상태 + delta + resync | **기존 전체 스냅샷 방식 유지** | 현재 서버가 10Hz 전체 스냅샷을 보내고 `SnapshotGate`로 순서를 보장함. delta가 없으므로 resync도 필요 없음 |
| 보상 중복 방지 | 새로 설계 | **기존 `RewardService`를 그대로 사용** | 이미 기기별 로컬 저장이고 `runId` 기준으로 중복 지급을 막음 |
| 검증 순서 | 실기기 통신 실험부터 | 실기기 통신 실험과 **실기기 없이 하는 자동 테스트**를 병행 | 메모리 전송 계층으로 Host/Guest 전체를 Playwright·Vitest에서 검증할 수 있음 |

v1의 원칙은 그대로 유지한다. Unity 전환 금지, 외부 서버·STUN/TURN 금지, Host Migration 제외, 경기 중 참가 제외, LAN 작업 중 밸런스 변경 금지.

## 1. 제품 방향

**방장 폰이 판정을 맡는다. 참가자는 방코드 하나로 방장 폰에 직접 접속한다.**

1. 친구들이 같은 공유기 Wi-Fi에 접속하거나, 한 명이 핫스팟을 켠다.
2. 방장이 방을 만들면 8자리 코드가 나온다. 이 코드 안에 방장 폰의 LAN 주소가 들어 있다.
3. 참가자가 코드를 입력하면, 앱이 코드를 풀어 주소를 얻고 방장 폰에 바로 TCP로 접속한다.
4. 방장 폰은 기존 엔진으로 경기를 돌리고, 기존 프로토콜 그대로 스냅샷을 보낸다.

"서버 없음"은 **외부 상시 서버가 없다**는 뜻이다. 방장 앱 안에는 Host 로직(TypeScript)과 작은 TCP 리스너(네이티브)가 돈다.

## 4. 사용자 흐름

### 4.1 네트워크 준비

- 같은 공유기 Wi-Fi에 접속하거나, 한 명이 핫스팟을 켜고 나머지가 그 핫스팟에 접속한다.
- 핫스팟을 켠 사람이 방장이 되는 흐름을 우선 지원한다. 공유기 환경에서는 누구나 방장이 될 수 있다.
- 친구대전 화면에 "같은 Wi-Fi 또는 핫스팟에 연결해 주세요"를 짧게 표시한다.
- 인터넷 연결 여부로 참가를 막지 않는다.

### 4.2 방 만들기 (방장)

1. 친구대전 → 방 만들기
2. 필요하면 로컬 네트워크 권한을 요청한다 (8.3).
3. 네이티브 TCP 리스너를 연다. 성공하면 실제 바인딩된 LAN 주소와 포트를 받는다.
4. 주소·포트로 방코드를 만든다 (6장).
5. 대기실에 코드, 방장 표시, 참가자, 정원(최대 4)을 표시한다.
6. 사람이 2명 이상 모이면 시작 버튼이 켜진다.

리스너가 실제로 열리기 전에는 코드를 보여주지 않는다. 열기에 실패하면 이유를 안내하고 연습 모드로 돌아갈 수 있게 한다.

### 4.3 방 참가 (참가자)

1. 친구대전 → 코드 입력 → 입장
2. 코드를 디코딩한다. 형식이나 검사값이 틀리면 **즉시** "코드를 다시 확인해 주세요"를 표시한다. 네트워크 대기 없이 바로 판정한다.
3. 디코딩한 주소로 TCP에 접속한다. 진행 표시는 "연결 중"이며 취소할 수 있다.
4. `hello` 핸드셰이크에서 프로토콜 버전·앱 버전·정원·방 상태를 확인한다.
5. Host가 승인하면 대기실에 들어간다.

IP·포트는 일반 화면에 노출하지 않는다. 개발 진단 화면에서만 보여준다.

### 4.4 경기와 재경기

- 방장이 시작하면 기존 `room:start` → 카운트다운 → `match:init` → `match:snapshot` 흐름을 그대로 따른다.
- 사망 후 재시도는 기존 `run:retry` 경로를 쓴다.
- 결과 화면이 끝나면 같은 방에서 다음 라운드를 하거나 나간다. 새 라운드는 새 `matchId`를 쓰고, 이전 경기의 입력·결과는 무시한다.
- 방을 닫을 때는 리스너, 모든 소켓, Host 루프, 타이머를 정리한다.

│                 │ LoopbackTransport         │        │                │ LanTransport │

| 전송 인터페이스 | `src/client/transport.ts` (신규) | 이벤트 송수신 추상화 | 신규, 작음 |
| 전송 구현 | `SocketIoTransport` / `LoopbackTransport` / `LanTransport` / `MemoryTransport`(테스트용) | 실제 송수신 | 신규 |
| 네이티브 소켓 | Capacitor 플러그인 `LanSocket` (Kotlin/Java) | TCP 리슨·접속·프레임 송수신 | 신규 |

**원칙: 네이티브 플러그인은 바이트를 옮기기만 한다.** 게임 규칙, 방 상태, 봇은 네이티브에 두지 않는다.

### 5.1 방 관리 공통화 (`RoomCore`)

**결정 (2026-10-10, 구현됨):** `RoomManager` 전체를 `src/shared/rooms.ts`로, 경기 루프를 `src/shared/room-loop.ts`로 옮겼다. 서버와 LAN Host가 같은 코드를 쓴다. 아래는 원래 계획이다.

`rooms.ts`에서 순수 로직만 추출해 `RoomCore`로 만든다. 서버와 LAN Host가 같은 코드를 쓰게 하기 위해서다.

- `node:crypto`의 `randomUUID`/`randomBytes`/`randomInt`는 주입식 `Random` 인터페이스로 바꾼다. 브라우저에서는 `crypto.getRandomValues`로 구현한다.
- `Session`·socket 참조는 `memberId` 기반의 얇은 인터페이스로 바꾼다.
- 기존 `RoomManager`는 `RoomCore`를 감싸는 서버 어댑터가 된다. **동작 변경 없음**을 기존 서버 테스트로 확인한다.
- 이 추출이 기존 서버에 회귀 위험을 키운다고 판단되면 대안을 쓴다. `LanRoom`을 별도로 만들고 `rooms.ts`와 같은 공용 함수(`createMatch`, `botSpecs`, `leaveParticipant`, `retryHumanRun`, `trySpawn`, `roundDeadlineTicks`)만 호출한다. 어떤 쪽을 택했는지 0단계 기록에 남긴다.

### 5.2 전송 인터페이스

`NetworkSession`이 socket.io를 직접 부르지 않고 아래 인터페이스를 쓰도록 바꾼다. 이벤트 이름과 페이로드는 기존 `ClientEvents`/`ServerEvents`를 그대로 쓴다.

```ts
interface GameTransport {
  connect(): Promise<void>;
  request<E extends keyof ClientEvents>(event: E, payload: ..., timeoutMs: number): Promise<Ack>; // ack가 있는 명령
  send<E extends keyof ClientEvents>(event: E, payload: ...): void;   // input:direction 등
  on<E extends keyof ServerEvents>(event: E, handler: ...): () => void;
  onClose(handler: (reason: CloseReason) => void): () => void;
  close(): void;
}
```

- `SocketIoTransport`: 기존 동작 그대로. 웹 빌드의 온라인 경로.
- `LoopbackTransport`: 방장 자신의 클라이언트용. 네트워크 없이 `LanHost`를 직접 호출한다. 실제 전송과 순서가 같도록 microtask로 비동기 전달한다.
- `LanTransport`: `LanSocket` 플러그인 위에서 JSON 프레임을 주고받는다.
- `MemoryTransport`: 테스트 전용. Vitest에서는 메모리 큐로, Playwright에서는 같은 context의 두 페이지 사이 `BroadcastChannel`로 연결한다.

**Host 본인의 입력도 `LoopbackTransport`를 거쳐 Guest와 같은 검증 경로(`attachDirection`과 같은 규칙)를 탄다.**

## 6. 방코드 = 주소 (Discovery 제거)

### 6.1 인코딩

기존 형식은 8자리, 문자 32종(`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, 문자당 5비트)이다. 총 40비트를 다음처럼 나눈다.

| 자리 | 비트 | 내용 |
| --- | --- | --- |
| 1–7번째 문자 | 35 | Host IPv4(32비트) + 포트 슬롯 0–7(3비트). 실제 포트 = `LAN_BASE_PORT + 슬롯` (예: 47610–47617) |
| 8번째 문자 | 5 | 검사 문자: 앞 7문자에 대한 **Luhn mod 32** |

인코딩 순서는 다음과 같다.

1. 35비트 데이터를 만든다.
2. 고정 상수와 XOR해서 섞는다. 같은 대역의 코드가 서로 비슷해 보이지 않게 하려는 것이고, 보안 목적은 아니다.
3. 7문자로 바꾼다.
4. 7문자로 검사 문자를 계산해 8번째에 붙인다.

- **구현은 `BigInt` 또는 바이트 배열로 한다.** JS의 일반 비트 연산자(`^`, `<<`, `>>`)는 32비트로 잘리므로 35·40비트 값에 쓰면 안 된다.
- **오타 검출 범위:** Luhn mod 32는 **한 문자 오타를 모두** 검출하고, 인접한 두 문자 뒤바뀜도 대부분 검출한다. 그 밖의 오타는 약 1/32 확률로 검사를 통과할 수 있다. 통과한 잘못된 코드는 연결·핸드셰이크 제한시간 안에 실패로 안내한다 (AC04).
- Host는 슬롯 0부터 차례로 바인딩을 시도하고, 성공한 슬롯을 코드에 넣는다.
- 인코더/디코더는 `src/shared/lan-code.ts`에 순수 함수로 둔다. 테스트는 다음을 포함한다.
  - 왕복 변환
  - 모든 위치·모든 문자의 한 문자 치환 전수 검출
  - 경계 주소(`0.0.0.0`, `255.255.255.255`, 슬롯 7)
- 기존 서버 정규식 `^[A-HJ-NP-Z2-9]{8}$`와 형식이 같아서 입력칸·검증 UI를 그대로 쓸 수 있다.

### 6.2 이 방식으로 사라지는 문제

| v1에서 다뤄야 했던 것 | v2 |
| --- | --- |
| 핫스팟에서 멀티캐스트/브로드캐스트가 막힘 | 쓰지 않음 |
| 같은 코드의 방이 여러 개 보임 | 주소가 다르면 코드도 다름. 충돌이 구조적으로 없음 |
| 광고 만료·목록 정리 | 광고 자체가 없음 |
| 검색 제한시간 | 연결 제한시간 하나만 남음 |

### 6.3 한계와 처리

- **방장의 IP가 바뀌면 코드도 바뀐다.** 네트워크가 바뀌면 방을 다시 만든다는 v1 정책과 같다.
- **같은 방장이 방을 다시 열면 이전 코드로도 들어올 수 있다.** 같은 친구의 방이므로 허용한다. 실제 방 식별은 핸드셰이크에서 받는 `roomId`로 한다.
- **IPv6 전용 네트워크는 지원하지 않는다.** Android 핫스팟과 일반 공유기는 IPv4 사설 주소를 주므로 P0 범위에서는 문제없다. 사설 IPv4 주소를 찾지 못하면 방 만들기를 실패 처리하고 안내한다.
- **방코드는 인증 수단이 아니다.** 같은 LAN의 누구든 코드를 알면 접속을 시도할 수 있다. 참가 확정은 정원·상태·버전 검사 후 Host가 한다. 친구끼리 하는 게임이라는 범위에서 충분하다.

### 6.4 방장 주소 고르기 (네이티브)

**리슨 주소와 코드에 넣을 주소는 별개다.** 리스너는 와일드카드(`0.0.0.0`)로 열고, 코드에는 참가자가 실제로 접속할 주소 하나만 넣는다.

주소는 다음 순서로 고른다.

1. **공유기 Wi-Fi 방장:** `ConnectivityManager`에서 `TRANSPORT_WIFI` 네트워크를 찾고, 그 `LinkProperties`의 IPv4 주소를 쓴다. OS가 알려 주는 값이므로 확정 경로다.
2. **핫스팟 방장:** AP 인터페이스 주소를 알려 주는 공개 API가 없다. 그래서 `NetworkInterface` 목록을 다음 조건으로 거른다.
   - up 상태, loopback 아님, IPv4 사설 대역(10/8, 172.16/12, 192.168/16)
   - VPN·터널·셀룰러로 보이는 인터페이스 제외: `tun*`, `ppp*`, `ipsec*`, `rmnet*`, `ccmni*`, `dummy*` 등. 그리고 `TRANSPORT_VPN`·`TRANSPORT_CELLULAR` 네트워크의 `LinkProperties`에 속한 인터페이스
   - 1번에서 이미 고른 Wi-Fi 클라이언트 인터페이스 제외
3. **최종 후보가 정확히 하나일 때만 코드를 발급한다.** 후보가 0개이거나 2개 이상이면 **임의로 고르지 않는다.** 이때 방 만들기는 "이 기기에서 방 주소를 찾지 못했어요. 다른 친구가 방을 만들어 주세요"로 실패한다. 후보 목록은 개발 진단 화면과 로그에 남기고, 해당 기기 모델은 1단계 매트릭스에 "주소 선택 실패"로 기록한다.
4. **자기 접속 확인:** 코드를 표시하기 전에, 고른 주소·포트로 방장 자신이 TCP 접속과 `lan:hello`를 한 번 왕복해 본다. 다른 기기에서 접속할 수 있다는 보장은 아니지만, 엉뚱한 인터페이스나 바인딩 실패는 여기서 걸러진다.

**`192.168.43.1` 같은 값을 하드코딩하지 않는다.** 인터페이스 이름 목록도 판단 보조일 뿐 정답 목록이 아니다. 1단계에서 기기별 실제 인터페이스 이름을 기록해 필터를 보정한다.

## 7. 네이티브 전송: `LanSocket` 플러그인

### 7.1 왜 TCP 하나인가

- WebRTC를 쓰면 SDP/ICE를 주고받을 signaling 채널이 따로 필요하다. 그 채널이 어차피 로컬 TCP다. 그렇다면 게임 데이터도 그 TCP로 보내는 게 계층 하나를 줄이는 길이다.
- Chromium/WebView는 host ICE 후보를 mDNS(`*.local`) 이름으로 숨긴다. 핫스팟에서 이 이름을 못 풀면 연결이 실패한다. 피할 수 없는 위험이다.
- 네이티브 소켓은 WebView의 mixed content·cleartext 정책을 거치지 않는다. Capacitor의 `https://localhost` 기본 스킴을 바꾸지 않아도 된다.
- **TCP의 한계:** TCP는 순서를 보장한다. 그래서 이미 소켓에 써 버린 데이터는 앞부분의 재전송이 끝날 때까지 뒤의 최신 스냅샷도 함께 기다린다(head-of-line blocking). 앱이 이 지연을 없앨 수는 없다. 앱이 할 수 있는 일은 **소켓에 쓰기 전에 대기 중인 스냅샷이 쌓이지 않게 하는 것**과 **커널 송신 버퍼에 쌓이는 양을 줄이는 것**뿐이다 (7.3).
- 근거리 LAN은 손실·재전송이 드물다. 그래서 이 한계를 받아들이고 TCP를 유지한다. 실제로 화면이 얼마나 뒤처지는지는 1단계에서 측정한다. 측정 결과가 나쁘면 그때 UDP 스냅샷 채널을 P1로 검토한다.

### 7.2 플러그인 API (JS 쪽)

```ts
// Host
listen(opts: { basePort: number; slots: number }): Promise<{ address: string; port: number; slot: number }>;
closeServer(): Promise<void>;
// Guest
connect(opts: { address: string; port: number; timeoutMs: number }): Promise<{ connectionId: string }>;
// 공통
send(opts: { connectionId: string; data: string; replaceable?: boolean }): Promise<void>;
disconnect(opts: { connectionId: string }): Promise<void>;
// 이벤트
'connection'  { connectionId, remote }      // Host만
'message'     { connectionId, data }
'close'       { connectionId, reason }
```

- 프레임 형식은 `[4바이트 길이][UTF-8 JSON]`이다. 프레임 최대 크기를 정해 두고(예: 1MB), 넘으면 연결을 끊는다.
- 읽기·쓰기는 연결마다 백그라운드 스레드에서 처리한다. JS로 올리는 이벤트는 순서를 보장한다.
- 라이브러리 없이 `java.net.ServerSocket`/`Socket`으로 구현한다. 필요하면 Java-WebSocket 같은 검증된 라이브러리로 바꿀 수 있지만, P0에서는 의존성을 늘리지 않는다.

### 7.3 송신 큐 정책 (느린 참가자 대응)

연결마다 네이티브 송신 큐 하나와 송신 스레드 하나를 둔다.

- **교체는 소켓에 쓰기 전에만 한다.** `replaceable: true` 메시지(일반 `match:snapshot`)를 넣을 때 **큐의 맨 끝**이 같은 `matchId`의 교체 가능 스냅샷이면 그것만 새 것으로 바꾼다. 그 외에는 뒤에 붙인다.
  - 맨 끝만 보므로, 교체 불가 메시지(`match:init` 등)를 뛰어넘어 순서를 바꾸는 일이 생기지 않는다.
  - `matchId`가 다르면 교체하지 않으므로, 이전 경기 스냅샷이 새 경기의 `match:init` 뒤로 끼어드는 일도 없다.
  - 이미 소켓에 쓴 메시지는 되돌리지 않는다.
- `room:view`, `match:init`, `match:result`, ack, 신뢰성 스냅샷(10장)은 교체·삭제하지 않는다.
- **커널 버퍼 줄이기:** `TCP_NODELAY`를 켠다. 송신 버퍼(`SO_SNDBUF`)는 스냅샷 몇 개 분량으로 작게 잡는다. 소켓 쓰기가 막히면 메시지가 커널이 아니라 앱 큐에 머물러 교체 대상이 된다.
- **상한은 두 가지다. 하나라도 넘으면 그 참가자를 이탈 처리한다.**
  - 용량: 교체 불가 메시지 64개 또는 4MB
  - 나이: 큐에서 가장 오래 기다린 메시지가 3초 이상 (기존 클라이언트의 "3초 무스냅샷 = 불안정" 기준과 맞춤)
  - 한 명이 느리다고 Host 전체가 멈추면 안 된다. 상한값은 1단계 측정 후 조정하고 기록한다.
- 이 규칙은 기존 socket.io의 `volatile` 송신과 목적이 같다. 다만 이미 쓴 데이터는 TCP 순서에 묶인다는 점이 다르다.
- **측정 (1·4단계):** 연결이 유지되는지만 보지 않는다. 참가자 화면이 Host의 실제 틱보다 얼마나 뒤처지는지도 잰다. Guest 수신 시각 기준 `Host tick − 표시 tick`의 p50/p95/max, 교체 횟수, 큐 최대 나이를 기록한다.

### 7.4 Guest의 소켓을 Wi-Fi에 묶기 (중요)

Android는 **인터넷이 없는 Wi-Fi(핫스팟·오프라인 공유기)에 연결돼 있으면 기본 네트워크를 모바일 데이터로 잡는 경우가 있다.** 이때 사설 IP로 연결을 시도하면 셀룰러 쪽으로 나가서 실패할 수 있다.

- Guest의 `connect`는 `ConnectivityManager`로 `TRANSPORT_WIFI` 네트워크를 찾고, `Network.bindSocket()` 또는 `network.socketFactory`로 그 네트워크에 묶어서 연결한다.
- Host는 와일드카드 주소로 리슨하므로 따로 묶지 않는다.
- 모바일 데이터를 켠 상태 / 끈 상태를 둘 다 실기기로 검증한다 (AC03).

## 8. Android 앱

### 8.1 래퍼 구축 (신규)

- Capacitor를 추가한다(`@capacitor/core`, `@capacitor/android`, `@capacitor/cli`). `webDir`은 Vite 클라이언트 빌드 산출물로 지정한다.
- HTML/JS·이미지·폰트를 APK에 넣는다. **`server.url`(원격 로드) 설정을 넣은 빌드를 최종 APK로 내지 않는다.**
- 외부 CDN, 온라인 설정 조회, 개발 PC가 없어도 실행돼야 한다. 비행기 모드 + Wi-Fi만 켠 상태로 확인한다.
- 런타임 판별: `Capacitor.isNativePlatform()`이 참이면 친구대전이 LAN 경로를 쓴다. 웹 빌드는 지금처럼 온라인 서버를 쓴다. "빠른 대전(공개)"은 APK에서는 숨기거나, 서버 주소가 설정됐을 때만 표시한다.
- 기존 웹 빌드·온라인 서버·Playwright 테스트 경로를 깨지 않는다.

### 8.2 수명주기

- 앱이 백그라운드로 가면 (`App` 플러그인의 `appStateChange` 또는 `visibilitychange`):
  - **Host**: 참가자 전원에게 `room:closed`(이유: 방장이 앱을 나감)를 **보내 보고** 리스너를 닫는다. OS가 앱을 바로 멈추면 이 알림이 도착하지 않을 수 있다. 그런 Guest는 기존 5초 heartbeat 타임아웃으로 종료한다.
  - **Guest**: 연결을 닫고, 돌아오면 메뉴에서 안내한다.
- 경기 중에는 화면 꺼짐을 방지한다 (P0. 경기 화면에서만).
- 방장에게만 "앱을 나가면 친구들의 경기도 끝나요"를 한 줄 표시한다.

### 8.3 권한과 OS 버전

- Manifest: `INTERNET`(로컬 소켓에도 필요), `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`.
- Android 16의 로컬 네트워크 보호 opt-in과 Android 17(target SDK 37 이상)의 로컬 네트워크 권한 요구사항을 공식 문서[S1] 기준으로 반영한다. 권한 이름과 요청 시점은 구현 시점의 문서로 확정한다.
- 권한은 친구대전에 들어갈 때 설명하고 요청한다. 거부해도 연습 모드는 정상 동작해야 한다.
- "Wi-Fi에 연결됨"만 검사해서 핫스팟 방장을 오프라인으로 잘못 판단하지 않는다.

## 9. Host 로직

### 9.1 권한 범위

Host 한 대만 이동·충돌·선·점령·사망·재스폰·봇·라운드 종료를 확정한다. Guest가 보낸 좌표·영토·킬·코인은 믿지 않는다. 받는 입력은 기존 `input:direction`(matchId, lifeId, seq, dx, dy)과 기존 명령들뿐이다. 검증 규칙은 `transport.ts`의 `attachDirection`과 `protocol.ts`의 `validDirection`/`validRequest`를 그대로 쓴다.

### 9.2 경기 루프

`LanHost`의 루프는 `PracticeSession.advance`의 패턴을 따른다.

- `requestAnimationFrame`으로 시간을 재고, `1/simulationHz` 간격으로 누적 틱을 돌린다. 한 번에 최대 5틱, 1초를 넘는 정지는 리셋한다.
- 봇 입력은 `observeBotForTick` → `getBotInput`. Practice·서버와 같은 호출이다.
- `simulationHz / snapshotHz` 틱마다 `buildView` → `packSnapshot`을 한 번만 만든다. 참가자별로는 `selfParticipantId`·`lastAppliedInputSeq`만 바꿔서 보낸다. 서버 `publishSnapshot`과 같은 방식이다.
- 규칙·속도·봇 판단 주기(`botDecisionMs`)는 바꾸지 않는다.
- Web Worker 분리는 P1이다. 4인 측정에서 메인 스레드 틱 비용 때문에 프레임이 떨어진다는 근거가 나왔을 때만 검토한다.

### 9.3 성능 예산

- 방장 폰은 렌더링 + 14슬롯 시뮬레이션 + 봇 + 직렬화 + 송신 + (핫스팟)을 모두 맡는다.
- 시뮬레이션·봇 비용은 **지금 Practice 모드에서 이미 폰이 감당하는 양과 같다.** LAN이 새로 더하는 비용은 스냅샷 직렬화와 브리지 전송뿐이다.
- 0단계에서 같은 기기의 Practice 모드 FPS·틱 비용을 기준선으로 잰다. LAN Host의 추가 비용은 그 기준선과 비교해서 판단한다.
- 스냅샷 크기는 기존 `metrics.snapshotBytes` 방식으로 잰다. 크기가 브리지 병목이 되면 순서대로 줄인다.
  1. 참가자 공통 본문은 한 번만 브리지로 넘기고, 네이티브가 참가자별 머리말만 붙이는 `broadcast` API를 추가한다 (P1).
  2. 그다음 직렬화 비용을 줄인다.
- 봇 수·맵 크기 조정은 밸런스 결정이다. 성능 대책으로 몰래 바꾸지 않는다.

### 9.4 봇·참가·이탈

- 봇 수 = `maxSlots(14) − 사람 수`. 사람 2명이면 봇 12, 4명이면 봇 10.
- 경기 중 신규 참가는 받지 않는다 (`BAD_PHASE`, "이미 경기가 시작되었습니다").
- 사망 후 재시도는 기존 HUMAN 흐름이다. 연결이 유지되는지와는 별개다.
- Guest 연결이 끊기면 경기는 계속한다. 그 자리는 **기존 서버와 같은 방식으로 봇으로 교체한다**(`rooms.ts` `replaceWithBot`, 같은 slot 유지). 2026-10-10 사용자 결정으로 v2.1의 "빈자리로 둠"을 바꿨다. 이유: 온라인과 동작을 맞추고 14슬롯 밀도를 유지한다.
- 사람이 Host만 남아도 경기는 계속할 수 있고, 메뉴로 나갈 수 있다.

## 10. 동기화

**기존 프로토콜을 그대로 쓴다.** 새 메시지는 LAN 핸드셰이크와 종료 알림뿐이다.

### 10.1 메시지

| 메시지 | 방향 | 상태 |
| --- | --- | --- |
| `lan:hello` / `lan:welcome` | Guest ↔ Host | **신규. 연결 확인만 한다.** `protocolVersion`과 앱 버전을 확인하고 연결 ID를 발급한다. 참가자 등록은 하지 않는다 |
| `room:join`, `room:start`, `room:leave`, `run:retry` + ack | 기존 | 그대로. **참가자 등록은 기존처럼 `room:join`이 한다** (닉네임 검증, 정원·페이즈 검사 포함) |
| `room:view` | Host → 전원 | 그대로 |
| `match:init`, `match:snapshot`, `match:result` | Host → Guest | 그대로 (전체 스냅샷, `SnapshotGate`로 순서 보장) |
| `input:direction` | Guest → Host | 그대로 |
| `lan:ping` / `lan:pong` | 양방향 | **신규.** 1초 간격, 5초 무응답이면 끊김 |
| `room:closed` | Host → 전원 | **신규.** 종료 이유 코드 |

- `PROTOCOL_VERSION`은 LAN 메시지를 추가할 때 올린다. 버전이 다르면 `PROTOCOL_MISMATCH`, "앱 버전이 달라요. 같은 버전으로 맞춰 주세요"를 표시한다.

### 10.2 프레임 형식과 요청·응답 연결

TCP 프레임 하나에 JSON 객체 하나를 담는다. 종류는 세 가지다.

```jsonc
{ "k": "req", "id": 17, "e": "room:join", "d": { /* CommandRequest */ } }  // ack를 기다리는 명령
{ "k": "ack", "id": 17, "d": { /* Ack */ } }                               // 위 요청에 대한 응답
{ "k": "evt", "e": "match:snapshot", "d": { /* … */ } }                     // 응답 없는 이벤트 (input:direction 포함)
```

- `id`는 연결마다 송신 측이 1부터 올리는 정수다. 응답 `ack`는 같은 `id`를 돌려준다. socket.io의 ack 콜백과 같은 역할이다.
- 기존 `CommandRequest.requestId`(멱등성용)는 `d` 안에 그대로 둔다. 프레임 `id`와 섞지 않는다.
- 요청 제한시간은 기존 `NetworkSession.command`와 같은 3초다. 제한시간이 지나 늦게 도착한 `ack`는 버린다.
- 연결이 닫히면 대기 중인 요청은 모두 실패 처리한다.

### 10.3 전체 스냅샷으로 복구되는 것과 아닌 것

스냅샷이 매번 전체 상태이므로 delta 누락·resync·조각 재조립은 필요 없다. 다만 **다음 스냅샷에 남아 있는 상태만 복구된다.** 기준 커밋에서 정보 종류별로 확인했다.

| 정보 | 기존 코드에서 전달되는 방식 | 교체 가능 스냅샷이 빠지면 |
| --- | --- | --- |
| 영토·선·위치·생사·킬 | 매 스냅샷의 `owners`·`trailMasks`·`participants` | 다음 스냅샷이 복구 |
| 개인 run 결과 `RunResult` | `participants[].run.result`. `finishRun`이 정해진 뒤 `run:retry`로 새 run이 시작될 때까지 **상태로 남는다** (`src/shared/run.ts`, `retry.ts`) | 다음 스냅샷이 복구. 재시도 요청에 `runId`가 필요하므로, 클라이언트가 결과를 보기 전에 결과가 사라질 수 없다 |
| 경기 종료·최종 순위 | `phase === 'FINISHED'` 스냅샷이 **신뢰성 전송**됨. 이어서 `match:result`도 신뢰성 전송됨 (`loop.ts`) | 교체 대상이 아님 |
| 스폰 | 새 `SPAWN` 이벤트가 있는 스냅샷은 **신뢰성 전송**됨 (`loop.ts`) | 교체 대상이 아님 |
| 경기 시작 | `match:init` (신뢰성) | 교체 대상이 아님 |
| 재시도 직후 상태 | `run:retry` 성공 시 신뢰성 스냅샷 (`app.ts`) | 교체 대상이 아님 |
| 점령·사망 **연출 이벤트** `events[]` | 최근 1초(30틱), 최대 64개 창으로 매 스냅샷에 반복 포함. `SnapshotGate`가 `eventId`로 중복을 제거 (`life.ts`, `protocol.ts`) | 1초 안에서는 다음 스냅샷이 복구. 1초 넘게 막히면 **연출만** 빠지고 판정 상태는 위 행들로 복구됨 |

- 결론: 보상과 판정에 영향을 주는 단발성 정보는 이미 지속 상태이거나 신뢰성 메시지로 전달된다. LAN Host도 **신뢰성 판정 규칙을 `loop.ts`와 똑같이 따른다.** 스폰 이벤트, `FINISHED`, `match:init`, 재시도 직후, `match:result`가 대상이다.
- 이 표는 2단계 자동 테스트로 고정한다. 교체 가능 스냅샷을 무작위로 버리는 `MemoryTransport` 모드를 만들고, `RunResult`·최종 결과·보상이 정확히 한 번 반영되는지 확인한다.
- 원격 플레이어 보간은 기존 `interpolationMs`/`maxExtrapolationMs` 설정을 그대로 쓴다.
- 클라이언트의 기존 "3초 동안 스냅샷이 없으면 불안정 표시"도 그대로 둔다.

## 11. 결과·보상

- 새 경제 규칙을 만들지 않는다. 기존 `REWARD_RULES`(기본 5, 영토 %당 2, 킬당 3, 클래식 클리어 100)를 그대로 쓴다.
- 각 기기는 자기 `selfParticipantId`의 `RunResult`만 기존 `RewardService`로 처리한다. `runId` 기준 중복 방지가 이미 있다. `RunResult`가 스냅샷 손실과 무관하게 도착하는 근거는 10.3에 있다.
- Host는 다른 사람의 잔액·인벤토리를 보내거나 받지 않는다. 장착 마커·색상은 닉네임처럼 참가 시 표시 정보로만 주고받는다. 이 부분은 기존 온라인 경로가 하는 범위와 같게 맞춘다.
- 연결이 끊길 때 확정되지 않은 성과로 보상을 추정해 만들지 않는다. 이미 지급한 보상을 되돌리지도 않는다.
- 중앙 서버가 없으므로 부정행위 방지 수단은 없다. 친구끼리 하는 게임이라는 범위로 받아들인다.

## 14. 구현 단계

단계마다 변경 내용, 검증 결과, 미검증 항목을 짧게 기록하고 다음 단계로 넘어간다. 1단계와 2단계는 서로 독립적이어서 **병행할 수 있다.**

### 0단계 — 기준선 (짧게)

- 기준 커밋을 정하고 `npm run typecheck`, `npm test`, 기존 e2e를 통과시킨다.
- 테스트 기기에서 Practice 모드의 FPS·틱 비용을 측정한다 (9.3 기준선).
- 기존 서버 경로로 R56·14슬롯 스냅샷의 평균·최대 바이트를 측정한다.
- `RoomCore` 추출과 `LanRoom` 대안 중 하나를 고르고 이유를 기록한다 (5.1).

### 1단계 — Android 통신 스모크 (실기기, 가장 큰 미지수부터)

- Capacitor 래퍼를 만들고, 오프라인으로 실행되는 APK가 기존 Practice 모드를 돌리는지 확인한다.
- `LanSocket` 플러그인과 `lan-code` 인코더를 구현하고, 숨겨진 개발 화면에서 다음을 확인한다.
  - 방장: 리슨 → 주소 선택(6.4, 후보 목록 기록) → 자기 접속 확인 → 코드 표시
  - 참가자: 코드 입력 → 접속 → ping/pong 왕복 → 40KB대 메시지를 10Hz로 연속 송수신
  - 송신 측 틱 번호를 실어 보내고, 수신 측 지연·교체 횟수·큐 최대 나이를 기록한다 (7.3 측정 항목)
- **검증 매트릭스:** {공유기, 방장 핫스팟} × {참가자 모바일 데이터 켬, 끔} × {방장↔참가자 역할 교차}
- **완료:** 매트릭스 결과표(기기·OS·WebView 버전 포함). 실패한 칸은 원인과 함께 기록한다. PC 브라우저 성공은 완료 근거가 아니다.

### 2단계 — 전송 추상화 + 브라우저 Host (실기기 없이 자동 테스트)

- `GameTransport`를 도입하고 `NetworkSession`을 이 인터페이스로 옮긴다. `SocketIoTransport`로 **기존 온라인 e2e가 그대로 통과**해야 한다.
- `RoomCore`(또는 `LanRoom`), `LanHost`, `LoopbackTransport`, `MemoryTransport`를 구현한다.
- 자동 검증:
  - Vitest: 코드 인코딩 왕복·한 문자 오타 전수 검출, 입력 검증(matchId·lifeId·seq), 정원·페이즈 거부, 이탈 정리, 보상 중복 방지, 송신 큐 교체 규칙(맨 끝 교체만 허용, `matchId` 경계 유지), 요청·응답 `id` 연결과 제한시간
  - 손실 주입: `MemoryTransport`가 교체 가능 스냅샷을 무작위로 버려도 10.3 표대로 복구되고 보상이 한 번만 지급되는지 확인
  - Playwright(같은 context의 두 페이지, BroadcastChannel): 방 생성 → 참가 → 시작 → 이동·점령·사망·재시도 → 라운드 종료 → 재경기, Guest 이탈, Host 종료
- **완료:** 위 테스트 통과, 기존 Practice·온라인 회귀 없음.

### 3단계 — 통합

- `LanTransport`로 1단계 플러그인과 2단계 Host를 연결하고, 친구 카드 UI를 APK의 LAN 경로에 붙인다.
- 실기기 2대로 정상 흐름, 잘못된 코드, 정원 초과, 버전 불일치, 진행 중 참가, 취소·재시도를 확인한다.
- **완료:** 일반 사용자 흐름에서 IP 입력 없이 코드만으로 참가하고 한 판을 끝까지 한다.

### 4단계 — 수명주기·4인·발열·보상

- 백그라운드·화면 잠금·Host/Guest 이탈, 15분 연속 플레이, 재경기·방 닫기 반복, 4대 접속을 확인한다.
- 9.3 기준선 대비 Host 추가 비용, 스냅샷 크기, 송신 큐 상한 도달 횟수를 측정한다.
- **완료:** 지원 범위·측정 결과·남은 한계를 보고서로 남긴다. 실기기 확인에는 APK와 재현 절차를 함께 제공한다.

| AC05 | 2명 / 4명 | 정원·봇 수(12/10)·참가자 ID가 정확하고 중복 참가 없음 |
| AC06 | 점령·사망·선 절단 | 모든 기기 화면이 Host 확정 상태와 일치 |
| AC07 | 스냅샷 손실·지연 | 10.3 표대로 복구. 교체 불가 메시지는 순서대로 모두 도착. 화면 지연(`Host tick − 표시 tick`) p95를 기록하고 목표 200ms 이내 |
| AC07b | 주소 선택 실패 | 후보가 0개이거나 여러 개인 기기는 코드를 발급하지 않고 안내. 연결 안 되는 코드를 내보내지 않음 |
| AC08 | 사망과 재시도 | 기존 HUMAN 정책 유지. 네트워크 이탈과 구분됨 |
| AC09 | Host 종료 | 명시적 종료는 즉시, 갑작스러운 단절은 5초 안팎으로 안내 |
| AC10 | Guest 종료 | 나머지는 계속하고 이탈자는 정상 정리 |
| AC11 | 권한 거부 | 명확한 안내, 메뉴·연습 모드 정상 |
| AC12 | 재경기·방 닫기 10회 반복 | 남은 루프·리스너·소켓·타이머 없음 |
| AC13 | 결과·보상 | 결과를 다시 받거나 화면에 다시 들어가도 한 번만 지급 |
| AC14 | 15분 연속 | 크래시 없음, 송신 큐가 계속 늘지 않음, 초반·후반 성능 기록 |
| AC15 | Host 성능 | 선정 기기에서 30 FPS 이상, Host 틱 p95가 틱 예산(33ms) 안 |
| AC16 | 기존 기능 | 웹 빌드·온라인 서버·Practice·상점·장착 회귀 없음 (기존 테스트 통과) |
| AC17 | 외부 의존 | 중앙 서버·개발 PC·외부 ICE/CDN 없이 동작 |

최소 두 종류의 Android 기기로 방장·참가자 역할을 바꿔 가며 검증한다. 기기 모델·OS·WebView 버전·네트워크 종류를 기록한다. "모든 핫스팟에서 동작"으로 일반화하지 않는다.

## 17. 개발 로그 항목

개발 빌드에서만 수집한다. IP와 세션 정보는 공개 보고서에서 가린다.

- 기준 커밋, 앱 버전, `PROTOCOL_VERSION`, `roomId`/`matchId`
- 기기 모델, OS/WebView 버전, 네트워크 종류(공유기/핫스팟), 모바일 데이터 상태
- 연결 소요 시간과 실패 단계(리슨, 디코딩, TCP 연결, 핸드셰이크)
- Host 틱 비용 p50/p95/max, 밀린 틱, FPS, Practice 기준선 대비 차이
- 스냅샷 바이트, 송신 큐 길이, 교체된 스냅샷 수, RTT
- 반복 후 남은 리스너·소켓·루프, 메모리 변화
- 초반과 15분 이후 성능, 가능하면 OS thermal 상태
- 자동 테스트로 확인한 것과 실기기로 확인한 것을 구분

## 18. 작업 원칙

1. 목표는 LAN 친구대전이다. 외부 서버 배포로 대체하지 않는다.
2. Unity·새 렌더러·새 언어로 범위를 넓히지 않는다.
3. 판정은 `src/shared` 엔진만 한다. 네이티브는 바이트만 옮긴다.
4. 가장 큰 미지수(Android 소켓·주소·권한)를 가장 먼저 실기기로 확인한다.
5. 실기기 없이 검증할 수 있는 것은 `MemoryTransport`로 자동 테스트한다. 실기기 확인을 사용자에게 전부 떠넘기지 않는다.
6. 기존 웹 빌드·온라인 서버·Practice 경로를 지우거나 동작을 바꾸지 않는다.
7. LAN 작업 중 스폰·봇·경제·맵 크기를 바꾸지 않는다.
8. 외부 서비스 의존성을 자동으로 추가하지 않는다.
9. 미완료를 완료로 보고하지 않는다. 실기기로 확인하지 못한 것은 "미검증"으로 적는다.
