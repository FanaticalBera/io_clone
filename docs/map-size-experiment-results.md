# 맵 반경 단독 비교 실험 — 2026-10-03

## 방법과 범위

R22를 기본값으로 유지했다. R22/R28/R32/R36 각각 시드 4/19/73/115, Classic/Hold 각각 20분: 총 32회, 640분의 게임 시간이다. 정상 8 BOT 스폰과 기존 입력·movement·capture·death·respawn만 사용했다. 소유권, trail, 위치, bot goal을 직접 구성하지 않았다. AI, 인원, 초기 영역 19칸, 속도 4.2칸/초, 회전 9rad/s, 판단 200ms, 관찰 12칸, respawn 3초, 보호 2초, buffer 3칸, Classic 100%, Hold 50%/10초는 고정했다.

각 시드는 맵별 같은 참가자 성향/메모리 seed를 사용한다. 초기 앵커는 현재 코드의 고정 좌표를 유지한다. 따라서 초기 거리 자체를 확대하지 않았고, 경계까지의 여유와 후속 경로·respawn 공간만 달라진다. 첫 접촉 시점은 경계에 따른 기존 AI 경로 선택 때문에 달라질 수 있다.

이 표본에서는 어느 모드도 50%에 도달하지 않아 Classic/Hold의 이동 및 respawn 시계열이 동일했다. 반경마다 독립 시드는 4개이며 두 모드 결과를 독립 표본 8개로 부풀리지 않는다. 비교표와 구간 집계는 Classic 4개 시드를 사용한다. Hold의 별도 실행 기록도 원본 JSON에 보관했다.

## valid spawn center의 의미

`inspectSpawnSpace()`로 기존 trySpawn의 zone/safety 검사와 최적 위치 선택을 한 경로로 추출했다. 실제 trySpawn도 이 함수를 호출한다. 전체 19칸 neutral, trail 없음, control point 제외, reserved 제외, 살아 있는 상대 본체·선 및 reserved 영역과 buffer 거리 등의 기존 조건을 그대로 적용한다. 탐색 순서와 동일 safety의 tie break도 유지한다.

정기 관측은 현재 살아 있는 모든 참가자를 장애물로 보고, hypothetical dead 참가자에게 가능한 중심점을 센다. 이때 reserved는 비어 있다. 실제 respawn 시도 기록은 그 참가자와 해당 동시 batch의 reserved를 사용하므로 정확한 시도 전 count도 별도로 저장한다. 중심점 수는 서로 겹칠 수 있어 동시에 재등장할 수 있는 인원 수와 다르다. 참가자 상태·3초 지연·1초 retry·경기 phase 등 실행 자격은 기존 trySpawn/tryRespawns가 담당한다.

| 반경 | 정기 valid center 평균 / 최소 | 실제 시도 valid center 최소 | 시도 / 성공 / blocked 실패 | 후반 20% 시간 평균 ALIVE |
|---|---:|---:|---:|---:|
| R22 | 128.9 / 0 | 8 | 1055 / 1055 / 0 | 7.34 |
| R28 | 331.2 / 7 | 34 | 671 / 671 / 0 | 7.56 |
| R32 | 536.6 / 19 | 92 | 486 / 486 / 0 | 7.66 |
| R36 | 793.2 / 89 | 185 | 388 / 388 / 0 | 7.78 |

모든 실제 시도에서 성공 여부와 valid center > 0이 일치했고, 소유 수 검사도 통과했다. R22의 정기 관측에서는 5개 시점에 center가 0이었다. 예를 들어 시드 115의 575초에는 neutral 614칸(40.42%), DEAD_WAIT 1명인데 center는 0이다. 그 즉시 respawn할 자격은 없고 실제 시도 때는 다시 유효 공간이 존재했다. 이처럼 neutral 칸 수만으로 spawn 가능성을 판단할 수 없다. 1초 샘플 사이의 더 짧은 공간 소실은 정기 관측에 포함되지 않을 수 있으며, 실제 시도는 전부 기록했다.

R28 이상에서는 정기 count의 최소가 각각 7/19/89였다. 현재 20분 봇 경기에서 SPAWN_BLOCKED 발생·retry·blocked 유지 시간은 모두 0이다. 자연스러운 **지속적** late-game spawn suppression 발생 시점은 아직 확인하지 못했다. 큰 맵에서 spawn 가능한 공간이 더 오래 남을 가능성과 일치하며, 1등 80~95% 상황에 대한 증명은 아니다.

## 승리 조건과 spawn 설계 판단

모든 반경의 Classic 자동 경기에서 100% 승리는 관측되지 않았다. 어느 반경도 1등 50%에 도달하지 않았다. 따라서 50~70%, 70~80%, 80~90%, 90~95%, 95% 이상 구간과 Hold 50%에서 10초 유지·취소 공방은 **미도달 / 검증되지 않음**이다. 자동 경기에서 미도달한 사실로 인간의 자연 완주가 불가능하다고 결론내리지 않는다.

현재 자료에서 spawnRadius, buffer, respawn 지연 변경이나 점유율 기반 강제 차단의 필요성은 확인되지 않았다. 80~95%를 실제 사람이 만든 뒤 neutral 분포, center count, 재등장 성공을 관찰하는 후속 검증이 필요하다. 큰 맵의 같은 95%에는 더 많은 절대 중립 칸이 남으므로 자동으로 마무리가 쉬워진다고 가정하지 않는다.

SPAWN_BLOCKED의 인간 UX는 현재 안전한 19칸을 찾는다는 안내가 있다. 실제 blocked 지속 상황이 관측되면 관전 대상 전환, retry 안내, 재참여 시점 표시를 후속으로 검토한다. 이번에는 spectator UI나 추가 countdown 규칙을 구현하지 않았다.

## 수동 플레이 후보: R32 / R36

R32는 R22의 약 2.09배 면적이며 전체 사망/분이 13.25 → 6.08로 감소했다. R36은 약 2.63배 면적, 4.86회/분으로 더 넓은 쪽을 비교하기 좋다. R28도 8.40회/분으로 개선됐지만, 우선 중간 후보 R32와 넓은 후보 R36에서 Classic 마무리 시간, Hold 50%/10초의 체감, 전투가 너무 뜸한지 비교한다. 이것은 테스트 후보 선정이며 최종 기본값 결정이 아니다.

다음 수동 검증에서는 각 후보에서 Classic/Hold, 1 HUMAN+7 BOT 및 가능하면 2 HUMAN+6 BOT를 비교한다. 1등 50%, 70%, 80%, 90%, 95%에 실제로 도달한 경우 그 구간의 시도와 center 수를 추가 기록한다. 아직 사람이 직접 플레이한 체감 결과는 없다.

## 개발/테스트에서만 선택

기본값과 운영 `http://127.0.0.1:3003/`는 계속 R22다. 사용자 메뉴나 영구 설정을 추가하지 않았다. 개발 Vite에서 연습 게임은 `?experimentMapRadius=32&experimentSeed=4` 또는 `36`을 사용한다. seed는 같은 초기 배치를 비교하기 위한 선택 값이다. 개발 서버의 온라인 방은 `MAP_EXPERIMENT_RADIUS=32`, `MAP_EXPERIMENT_SEED=4`로 실행할 수 있다. compiled production + NODE_ENV=production에서는 URL과 이 환경변수를 모두 무시한다.

실행 예(프로젝트 PowerShell, bundled Node 24 경로를 PATH에 추가한 상태):

```powershell
npm run dev:client
# 연습: http://127.0.0.1:5173/?experimentMapRadius=32&experimentSeed=4
# 다른 터미널에서 개발용 온라인 서버를 사용할 경우:
```
