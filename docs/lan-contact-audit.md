# LAN 선 접촉 판정·탈락 표시 점검 — 2026-10-14

사용자 보고: S24+ 방장 / S21 게스트, 같은 Wi-Fi. 선을 밟아도 상대가 살아 있고 확실히 관통해야 죽는 느낌. 싱글에서도 원인을 알 수 없는 봇 사망 의심.

## 확인한 문제와 수정

방장도 엔진 결과를 직접 표시하지 않고 loopback 클라이언트로 스냅샷을 받는다. 엔진이 선 접촉 탈락을 확정한 뒤에도 기존 10Hz 스냅샷 주기까지 기다려서, 예측 중인 마커가 선을 더 지나간 뒤 탈락이 보일 수 있었다.

RoomLoop에서 새 DEATH 이벤트가 생긴 scheduler pass에 reliable 스냅샷을 보낸다. 일반 이동 갱신은 기존 10Hz를 유지하고, 같은 탈락 이벤트로 반복 전송하지 않는다. 충돌 규칙·무적·마커·효과·UI는 변경하지 않았다.

## 검증

- 실제 LanHost + 방장 loopback + 게스트 FrameTransport 회귀 테스트: 수정 전 엔진은 탈락했지만 두 클라이언트는 이전 스냅샷을 유지하여 실패. 수정 후 정기 갱신 사이의 틱에서 두 클라이언트 모두 탈락을 수신한다. reliable 전송, 중복 방지, 다음 일반 스냅샷의 replaceKey도 검사했다.
- 최종 전체 회귀: 108 파일, 737 통과 / 기존 expected fail 8. 현행 속도 경계 테스트와 판정 누락 감사도 포함한다. client/server/tests 타입 검사 통과. 웹·서버 및 Android debug APK 빌드 성공, S24+에 데이터 유지 업데이트 설치.
- 실기기: S24+ native 방장 + 같은 Wi-Fi의 PC TCP 게스트, 45초. 선 접촉 탈락 3건 모두 양쪽에서 같은 이벤트·스냅샷 번호로 수신. 정기 주기 밖의 스냅샷 301·335·947 틱에 전달했다. 이벤트 틱은 300·334·946이며 엔진은 step 종료 때 tick을 증가시키므로 이 차이는 다음 정기 갱신을 기다렸다는 뜻이 아니다.
- 현재 속도 4.41에서 여섯 방향 선 칸 경계 진입을 검사했다. 중앙을 관통하기 전에 EXISTING_TRAIL_CONTACT로 탈락했다.
- 현행 설정 R56 / 14명 / 속도 4.41에서 4개 seed·구성 조합을 각 1,800틱 실행: 사망 15건의 원인·선 마스크·영토·정리가 모두 규칙에 맞았다. 살아 있는 비보호 공격자가 살아 있는 상대의 선 칸에 남아도 탈락하지 않는 상태도 검사한다. 일반 이동과 봇 director를 사용하며, 혼합 구성은 스크립트 입력 인간 2명이다. 실제 싱글 세션의 재생은 아니다.

재실행: `node --import tsx tests/manual/contact-death-audit.mts`.

## 아직 확인하지 못한 것

이 수정은 **이미 확정된 탈락의 전달 지연**을 해결한다. 사용자가 보고한 **탈락 자체가 확정되지 않는 접촉**과 싱글의 갑작스러운 사망은 해당 장면을 재현하지 못했으므로 해결했다고 판단하지 않는다. S21 실기기는 이번 계측에 연결하지 않았다.

현재 선 접촉은 마커 중심이 선의 칸에 진입하는 것으로 판정한다. 그림자·펄스 등 바깥 효과의 겹침은 별도의 충돌 범위가 아니다. 클라이언트 예측 위치, 이미 점령되어 지워진 선의 이전 스냅샷, 부활 보호와 실제 판정 누락을 구분하려면 해당 접촉 시점의 엔진·표시 상태 기록이 필요하다. 추측으로 충돌 범위를 넓히지 않았다.
