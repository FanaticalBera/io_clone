# HEXHOLD 성능 기준선과 진행 결과

- PRD: [PERFORMANCE-PRD.md](PERFORMANCE-PRD.md) v0.4.2
- 기준 코드: `cb15860`(봇 동결). 작업 브랜치 `claude/mobile-game-performance-9c6a8f`
- 상태(2026-10-14): **단계 0·1, 단계 3 C2, 단계 2 렌더 본작업, 단계 4 1차 일부를 PC에서 완료. 실기기(S24+, S20+) 측정은 아직이다.** 모든 수치는 PC 기준이며, PRD의 판정은 실기기로 한다.
- 측정 환경 주의: 측정하는 동안 PC에 외부 부하(OneDrive WebView, 다른 에이전트 프로세스)가 있어 CPU 부하가 21~67% 사이에서 오르내렸다. 비교는 항상 같은 조건에서 번갈아 실행한 A/B로 했다.

## 3. 원인과 조치

### 3.1 시뮬레이션 (단계 3, 봇 행동 바이트 동일)

| 원인 (프로파일) | 조치 | 커밋 |
| --- | --- | --- |
| `plannedCapture`가 후보 경로마다 맵 전체 flood fill (봇 시간의 **61%**) | 경로 없는 flood를 소유 상태당 한 번 계산하고, 경로 옆에서 새로 갇히는 칸만 탐색. 원래 함수(`plannedCaptureFull`)와 결과 동일 | `88d781a` |
| 판마다 첫 안전 리스폰에서 반경 4 영역 표를 문자열 키 약 60만 개로 생성(PC 80ms) | "영역이 판 밖으로 나가는가"를 원점 거리 + 반경 > 맵 반경 산수로 판정, `region()`은 숫자 인덱스 | `234de1e` |
| `shortestPath`가 24칸 탐색에 맵 크기 배열 2개를 매번 할당·초기화 | 재사용 배열 + 호출 표시(stamp), 탐색 순서 동일 | `5cac436` |

검증: 무작위 비교 테스트(`tests/core/planned-capture.test.ts`, `spawn-geometry.test.ts`), 궤적 동일성 16/16(`evidence/perf-baseline/trajectory-*.json`), 기존 봇 테스트 전체.

C3(판단 분산 보정·분할)은 봇 동결 때문에 하지 않았다. 측정상 한 틱의 판단 봇 수와 비용의 상관은 약했고(판단 1회 비용이 원인), 그 비용은 위 조치로 줄었다.

### 3.2 렌더링 (단계 1, 2)

레이어별 비용(같은 세계를 멈추고 레이어를 하나씩 끔, 땅 4,214칸, DPR 1):

| 레이어 | 전 | 후 |
| --- | --- | --- |
| 영토 Graphics | 5.67 ms/프레임 (전체의 67%) | 약 0.6 ms (Blitter) |
| 판 테두리 | 1.12 ms | 약 0.4 ms (청크별 컬링) |
| 전체 | 8.50 ms | 1.7~3.6 ms (부하에 따라) |

| 조치 | PRD | 커밋 | 화면 영향 |
| --- | --- | --- | --- |
| 60fps 상한(남은 시간 이월, 120/90/144Hz 모두 60) | Q1 | `4e66938` | 120Hz 폰에서 120→60 |
| 메뉴·대기실·설정창·결과 화면에서 Phaser 정지(정지 화면) | Q2 | `4e66938` | 설정창·결과 뒤 화면이 멈춘 그림 |
| 색 스타일이 바뀔 때만 전체 다시 그리기 | Q4 | `4e66938` | 없음 |
| 영토를 색별 타일 Blitter로(선은 Graphics 유지) | G1(대안안) | `2dbd836` | 육각 테두리 안티앨리어싱 수준 차이(픽셀 1~2%가 8/255 초과) |
| 판 테두리·맵 가장자리선을 청크별로 나눠 컬링 | G1 확장 | `590f818` | 픽셀 동일 |
| 컬링 여유 16칸 → 3칸 | G2 | `d04ed48` | 없음(3배속 이동에도 빈 청크 0) |
| 선 이동만으로는 영토 타일을 다시 쌓지 않음 | G1 보완 | `2d873ce` | 없음(전체 재그리기와 동일) |

PRD와 다르게 한 결정:

- **G1은 RenderTexture 대신 Blitter(PRD의 대안안).** 메모리 예산, 화면 반영 지연, 해상도 변경 재생성 문제가 생기지 않는다. 땅이 바뀐 스냅샷에서 바로 반영된다. Phaser Blitter는 객체 확대율을 무시하므로 타일은 세계 단위 1 = 텍셀 1이다(바닥 타일과 같음).
- **4장의 "수신 처리 병합"은 생략.** PC에서 수신 처리 전체가 초당 17~21ms(JS의 4%)라 Gate 0 생략 기준에 해당한다. 그리기만 멈추고 수신 처리는 계속한다. 다시 그릴 때 최신 상태가 바로 보인다.
- **Q6(해상도 배율 상한)은 코드 기본값을 바꾸지 않았다.** 2026-10-04 선명도 작업으로 일부러 3배까지 올린 값이라, 측정용 빌드에 `?perfMaxDpr`만 넣었다. 실기기 발열·선명도 비교 후 정한다.
- **Q3(블러)은 유지.** 설정창·결과 화면에서 그리기가 멈추므로 블러 비용은 정지 화면 한 장분이다. 실기기에서 확인한다.

### 3.3 LAN 방장 (단계 4 1차 일부)

| 조치 | PRD | 커밋 |
| --- | --- | --- |
| 스냅샷 본문을 받는 사람 수만큼이 아니라 스냅샷마다 한 번만 직렬화(4인 방 4회 → 1회). 같은 프레임에 각자 자리 필드만 붙임 | N-a | `e67cdda` |
| base64를 32KB 덩어리로 생성(출력 동일) | N-d | `2d873ce` |
| 방장 루프를 10ms 고정 대신 다음 틱에 맞춰 깨움 | N-e | `2d873ce` |
| LAN 스냅샷 바이트 계측(직렬화량/송신량), 서버의 계측용 이중 직렬화 제거 | M1 | `a1a4a85` |

N-a는 LAN 프레임 안에서만 바뀐다. 온라인 서버 프로토콜은 그대로다. LAN은 같은 앱 버전끼리만 연결된다. 남은 N-b(방장 자기 화면 직통), N-c1(선 목록화, 온라인 프로토콜 변경 포함)은 실기기 LAN 측정(Gate 4-1) 후 정한다.

- [ ] **실기기 측정 (필수).** S24+, S20+에서 측정용 APK 두 개를 비교한다. 단계 0 APK는 `.local/perf/hexhold-perf-debug.apk`로 보관하고, 현재 APK는 `npm run build:apk:perf` 후 `assembleDebug`로 만든다.

- [ ] G4(점령 이펙트 상한)·G5(마커 단순화)는 PC 비중이 작았다(이펙트 1~2ms/s, 마커 약 0.4ms/프레임). 실기기 비중을 보고 진행 여부와 승인 여부를 정한다

## 5. 테스트

- 단위 테스트: 전체 708개 중 697 통과 + 기대 실패 8. 전체 병렬 실행 때 외부 부하로 무거운 시뮬레이션 테스트 1~5개가 20초 제한에 걸리는 일이 반복됐는데, 매번 단독 실행으로 통과를 확인했다. 실패하는 테스트 목록은 실행마다 다르고, 단계 0 전 코드에서도 같은 현상이 있다(예: `bot-phase01` 테스트는 단독 7초).
- e2e: 렌더 관련 spec(settings, camera, landscape, resolution, respawn-touch, mobile, territory-effects, player-color, marker-design)을 돌렸다. 실패는 모두 단계 1 이전 코드에서도 같이 실패하거나, 오래된 추적 `dist`(3001 포트)를 대상으로 하는 테스트였다. e2e 정비는 별도 세션이 맡고 있다.
