## 기록

### 2026-10-10 L01 시작

PRD v2.1 확정. task 문서 작성.

**기준 검사 (자동, PC, Node 24.21.0):** `npm run typecheck` 통과. `vitest run` 79파일 475개 통과.

**스냅샷 크기 (자동, PC):** 기본 설정 R56(9,577칸)·14슬롯, 봇 시뮬레이션 120초, 3틱마다 `packSnapshot` → `JSON.stringify` 길이.

| 사람 수 | p50 | p95 | max | build+pack+stringify p50/p95 | step p50/p95 |
|---|---|---|---|---|---|
| 2 | 47.3KB | 47.7KB | 48.0KB | 0.47 / 0.99ms | 0.50 / 15.6ms |
| 4 | 48.0KB | 48.4KB | 48.7KB | 0.47 / 0.81ms | 0.34 / 14.5ms |

- 크기는 경기 진행과 거의 무관하다. 대부분이 base64로 인코딩된 `owners`(1B/칸)와 `trailMasks`(2B/칸)다.
- 4인 방장 송신량은 약 48KB × 10Hz × 참가자 3명 ≈ **1.45MB/s**다. 1단계 스모크 부하를 "48KB × 10Hz × 연결 수"로 잡는다.
- 줄일 여지(P1): `trailMasks`는 대부분 0이라 압축 효과가 크다. 측정상 필요할 때만 한다.
- step p95 약 15ms는 봇 판단 주기에 몰리는 비용으로 보인다. 폰에서는 이보다 커질 수 있으므로, L02 APK의 Practice 모드에서 실기기 기준선을 잰다.

**RoomCore vs LanRoom 결정: LanRoom.** `RoomManager`는 서버 전용 정책과 `Session` 필드에 깊게 묶여 있다.
- 서버 전용 정책: 공개 방, 다중 방, 재접속 유예, 방장 이전, 빈 방 TTL
- `Session` 필드: `expiresAt`, `background`, `highestReceivedSeq` 등

LAN 정책은 이와 다르다. 방 하나, 방장 이탈 = 방 종료, 재접속 없음. 통째로 추출하면 서버 쪽 분기가 늘어 회귀 위험이 크다. 그래서 다음처럼 나눈다.
- 규칙이 어긋나면 안 되는 부분만 `src/shared/room-round.ts`로 뽑아 서버와 LAN이 같이 쓴다. 라운드 매치 생성(시드·봇 스펙·봇 메모리 시드·safe respawn 설정)과 이탈자 처리다.
- 페이즈 진행(WAITING→COUNTDOWN→RUNNING→RESULTS)은 `LanRoom`에 두고, 같은 `config` 값(`countdownSeconds`, `resultsSecondsIncludingCountdown`)을 쓴다.

**실기기 Practice 기준선 (실기기):** Galaxy S24+ `SM-S926N`, Android 15 (SDK 35), WebView 153.0.8010.57, 화면 384×832 CSS px @ DPR 2.81.
- 혼자 하는 Practice 진행 중 `requestAnimationFrame` 20초 측정(WebView 원격 디버깅): **119.9 fps**, 프레임 p50 8.3ms / p95 8.4ms / p99 8.5ms / max 13.4ms, 33ms 초과 프레임 0개. 열 상태 `Thermal Status: 0`.
- 직전 첫 측정에서는 4.6초짜리 프레임 1개가 있었다(나머지는 동일). 재현되지 않았고 visibility 변화도 없었다. 원인 미확인으로 기록해 두고, L12 장시간 측정에서 다시 본다.
- 연결 방식: 무선 디버깅(`adb pair`/`connect`). 이 기기는 "보안 위험 자동 차단"을 사용자가 테스트 기간 동안 끈 상태다.

**PRD와 기존 코드 충돌 → 결정됨 (2026-10-10):** 경기 중 나간 사람은 기존 서버처럼 **봇으로 교체**한다. PRD 9.4를 수정했고, `replaceWithBot`은 `room-round.ts` 공용 헬퍼로 옮겨 서버와 LAN이 같이 쓴다.

### 2026-10-10 L04·L05 단독 루프백 (실기기, S24+)

S24+ 한 대가 방장과 참가자를 동시에 맡았다. PC의 Windows 모바일 핫스팟(`192.168.137.x`)에 Wi-Fi 클라이언트로 연결된 상태였다. 다른 기기와의 LAN 통신은 아직 확인하지 않았다.

- 주소 선택: 후보 `wlan0=192.168.137.253 WIFI_CLIENT` 하나 → 코드 발급. `lo`는 제외됨.
- 리슨 포트 47610(슬롯 0). 자기 접속 확인 통과. 코드 `XWG8FSMH`로 접속, 연결 22ms, Wi-Fi 바인딩 사용.
- 20초 동안 10Hz × 48KB: 보낸 190개를 모두 받음(건너뜀 0), 1초 heartbeat 19개. 방장 큐 최대 3개/6ms, 교체 0회.
- RTT p50 41.2 / p95 58.5 / max 61.2ms. 화면 지연 p50 33.6 / p95 49.6 / max 55.1ms. 도착 간격 p95 112ms.
- **관찰:** 같은 기기 루프백인데도 RTT가 약 40ms다. 네트워크가 아니라 Capacitor 브리지(JS↔네이티브 이벤트 전달)와 48KB 문자열 처리 비용으로 보인다. 방장과 참가자를 한 기기가 동시에 맡아 비용이 두 배로 잡혔을 가능성이 있다. 2대 측정에서 다시 확인한다. 크게 나오면 PRD 9.3의 `broadcast` API와 스냅샷 압축의 우선순위를 올린다.
- 플러그인은 `ConnectivityManager.getAllNetworks()`(API 31부터 deprecated)를 쓴다. 지금 SDK 35/36에서는 동작한다. L11 전에 `NetworkCallback` 방식으로 바꿀지 판단한다.

### 2026-10-10 L04·L05 두 대 측정 (실기기)

- 네트워크: PC의 Windows 모바일 핫스팟(`192.168.137.0/24`). 두 폰 모두 Wi-Fi 클라이언트다. 공유기와 같은 구조지만 실제 공유기나 폰 핫스팟은 아니다.
- 결과는 위 매트릭스 1·2행. 60초 동안 손실·교체·큐 적체가 없었고, 화면 지연 p95는 55–60ms다(AC07 목표 200ms 이내).
- RTT p50이 35–40ms다. 같은 기기 루프백(41ms)과 비슷하므로 **대부분 Capacitor 브리지 비용이고 네트워크 비용은 작다.** 10Hz 게임에서는 감당할 수 있는 수준이다. 입력 지연에 직접 더해지므로 L08 이후 조작감 확인 때 다시 본다.
- 코드 모양 수정: XOR만으로는 인접 주소의 코드가 비슷하게 나왔다(`XWG8FSMH`/`XWG8FGVA`). 홀수 상수 곱셈(2^35 모듈러 전단사)을 추가했고 테스트 6개가 통과한다. 두 폰에 재설치함.

### 2026-10-10 S24+ 핫스팟 (실기기, 사용자가 직접 조작)

- **주소 선택:** 핫스팟 인터페이스 `swlan0`(`10.165.65.113`)가 후보 1개로 선택됐다. 셀룰러 CLAT 인터페이스 `v4-rmnet1/3`(`192.0.0.4/5`)는 제외됐다. 대역이 `192.168.43.x`가 아니라 `10.165.65.x`였다 → 하드코딩하지 않은 것이 맞았다. Samsung은 이 인터페이스를 `ConnectivityManager`의 Wi-Fi 네트워크로도 보고하는 것으로 보인다(분류 `WIFI_CLIENT`). 선택 결과에는 영향이 없다.
- **코드 오타 검출 실사용:** 사용자가 코드를 한 번 잘못 입력했고, 접속 시도 없이 `CHECK`로 즉시 거부됐다. 다시 입력해서 접속했다.
- **송수신:** 약 75초 동안 750/750, 지연 p50 44ms·p95 88ms. PC 핫스팟보다 꼬리 지연이 길다. 마지막 10초 p95 117ms, max 240ms다.
- **종료:** 사용자가 테스트를 끝내려고 Wi-Fi를 바꾸자, 참가자는 소켓 오류를 받았다. 이때 플러그인은 원인을 구분하지 않고 `REMOTE_CLOSED`로 기록했다. 방장은 큐 나이가 3초를 넘자 `SLOW_PEER_AGE`로 연결을 정리했다. 상한이 의도대로 동작했다.
- **수정:** 읽기 오류의 이유를 `REMOTE_CLOSED`(정상 종료, EOF)와 `NETWORK_ERROR`(네트워크 단절)로 나눴다. 다음 APK부터 반영.

### 2026-10-10 사용자 피드백 반영: 화면 잘림, 입장/퇴장 알림, 자리 비움, 방장 일시정지

사용자 결정: 참가자 자리 비움 30초, 방장 일시정지 60초. 진행 순서는 화면 수정 → 참가자 자리 비움 → 방장 일시정지.

**화면 (실기기 확인)**
- 방코드 타일이 대기실 왼쪽 열(약 360px)에 다 들어가지 않던 문제(온라인 친구 방도 같음) → 열 너비에 맞춰 줄어드는 4+4 타일.

- 홈 친구 카드 안내 문구 축약 → S20+(360px 높이)에서 카드가 다 보임.
- **기존 온라인 버그 수정:** 온라인에서 "다시 하기" 뒤 HUD·미니맵이 숨은 채로 남던 문제. `restartRun`의 온라인 경로가 연습과 달리 `ui.showGame`을 부르지 않았다. 이번 수정 전 master에도 있던 코드.
- 몰입 모드(시스템 바 숨김, 첫 스와이프는 바만 표시) → 실수로 홈으로 나가는 일을 줄임. APK는 가로 고정(`sensorLandscape`).
- 상단 알림: "OO님이 들어왔어요 / 나갔어요 / 잠시 자리를 비웠어요 / 돌아왔어요", "방장이 돌아왔어요". `RoomView.members[].away` 추가(온라인에도 적용).

**참가자 자리 비움 (자동 + 실기기)**
- 백그라운드 진입 → `control:background` → 온라인과 같이 봇이 귀환 전용으로 조종. 연결이 끊겨도 좌석을 30초 동안 유지(`reconnectGraceSeconds` 30).
- 참가자는 hello에서 받은 좌석 토큰으로 자동 재접속한다. 앱이 백그라운드인 동안은 재접속을 기다린다. 30초가 지나면 그 자리는 봇으로 교체된다.
- 실기기(S20+ 7초 백그라운드): 방장 화면에 "잠시 자리를 비웠어요" → "돌아왔어요".

**방장 일시정지 (자동 + 실기기)**
- 방장 백그라운드 → `LanHost.pause()`: 경기 정지, 참가자에게 `room:paused`. 참가자 화면에 "방장이 잠시 자리를 비웠어요. 기다리는 중… N초".
- 복귀 시 `resume()`: 벽시계 기준 기한(페이즈·빈 방·유예)을 정지한 시간만큼 뒤로 미루고 전원을 다시 동기화. 60초를 넘기면 방이 끝난다.
- **실기기에서 발견 1:** Android 15(S24+)는 백그라운드 앱의 네트워크를 약 5초 뒤 차단한다. 그래서 양쪽 TCP가 `NETWORK_ERROR`로 끊긴다. 앱 프로세스는 살아 있다. → 참가자는 일시정지 기한까지 좌석 토큰으로 계속 재접속을 시도한다. 방장은 복귀 시 같은 주소·포트로 리스너를 다시 연다(`ensureListening`, 방코드 유지). 네이티브 accept 오류에 500ms 백오프를 추가했다.
- **실기기에서 발견 2:** 백그라운드에서도 WebView 타이머가 돌아서, 일시정지 중 방장 자신의 루프백 클라이언트가 핑을 못 받고 5초 뒤 루프백을 닫았다. 그 결과 방이 종료됐다. → 일시정지 중에도 로컬 피어에는 핑을 보낸다.
- **수정 후 실기기(S24+ 15초 백그라운드):** 참가자 카운트다운 유지 → 방장 복귀 → 참가자 토큰 재접속(`lan_resumed`) → "방장이 돌아왔어요". 경기 계속.
- 테스트: `tests/core/lan-host.test.ts` 14개(좌석 유지·봇 교체, 토큰 재접속, 백그라운드 30초 초과, 일시정지·기한 이동, 60초 초과 종료, 일시정지 중 루프백 유지).
- 진단 로그: `[lan] …`가 logcat(Capacitor/Console)에 남는다. 개인정보는 없다.
