### 1.3 코드에서 찾은 원인 후보

모두 **가설**이다. 실제 비중은 단계 0 측정으로 확인한다.

**렌더링 (S1, S2)**

- R1. **영토를 매 프레임 다시 삼각형으로 분해한다.** 영토 청크는 `Phaser.Graphics`의 `fillPoints`/`strokePoints`로 그린다(`src/client/game-scene.ts` `drawView`). Phaser 3.90 WebGL의 Graphics는 내용이 바뀌지 않아도 매 프레임 경로를 다시 삼각형으로 쪼갠다(`MultiPipeline.batchFillPath`). 칸 하나당 육각형 채우기, 옆면 최대 2개, 외곽선을 그린다. 그래서 땅이 늘수록 프레임 비용도 커진다. 맵은 반지름 56, 약 9,600칸이다. 바닥(ground)은 같은 이유로 이미 Blitter로 바꿔 둔 상태다.
- R2. **컬링 여유가 넓다.** 화면 밖 16칸(청크 하나 크기)까지 그린다. 영토 이펙트와 점령 이펙트도 같은 값을 쓴다.
- R3. **프레임 상한이 없다.** Phaser, 연습 루프(`practice.ts`), 입력 루프(`input.ts`), frame meter가 각자 `requestAnimationFrame`을 쓴다.
- R4. **해상도 상한이 높다.** `renderPixelRatio`가 기기 배율을 최대 3배, 약 400만 픽셀까지 허용한다.
- R5. **매 프레임 다시 그리는 것들이 있다.**
  - 벽 하이라이트: 매 프레임 `clear()` 후 다시 그린다. 이때 `nearbyBoundaryEdges`가 경계선 전체를 걸러내고, `boundaryGeometry(...).edges.filter`도 같이 돈다.
  - 예측선: 매 프레임 지우고 다시 그린다.
  - `participants.find`: 프레임마다 여러 번 호출된다.
- R6. **점령 이펙트에 칸 수 상한이 없다.** 큰 땅을 먹으면 이펙트 칸 전체를 30Hz로 다시 그린다(마커 작업 때 미뤄 둔 항목).
- R7. **마커 하나에 Graphics가 4개씩 붙는다.** 애니메이션 마커는 매 프레임 이펙트를 다시 그린다. `mk:` 텍스처는 정리되지 않는다(마커 작업 때 미뤄 둔 항목).
- R8. **안 보이는데도 계속 그린다.** 메뉴, 결과, 대기실, 설정창에서도 Phaser가 최대 주사율로 돈다.

**설정창 (S3)**

- U1. **블러 뒤에서 캔버스가 계속 그려진다.** `dialog::backdrop{backdrop-filter:blur(2px)}` 뒤에서 캔버스가 계속 그려지니 블러도 매 프레임 다시 계산된다. 결과 화면(`#run-results`)도 같다.
- U2. **설정을 하나만 바꿔도 전체를 다시 그린다.** `settings.subscribe`가 어떤 설정이 바뀌든 `scene.refreshColors()`를 부른다. 그러면 영토 청크 전체와 미니맵 전체를 다시 그린다.
- U3. **닫는 순간 일이 한 프레임에 몰린다.** 닫을 때 `display()`, 일시정지 해제, U2의 전체 다시 그리기가 한 프레임에 겹친다.

**시뮬레이션·봇 (S1, S2, 틱 비용)**

- B0. **틱 평균 비용 자체가 크다 (v0.4 추가).** 봇 동결 시점 평균 3.37ms/tick(PC)이다. 30Hz면 PC에서 초당 약 100ms, 코어 하나의 약 10%를 시뮬레이션이 쓴다. 모바일은 PC보다 몇 배 느리므로 렌더링과 맞먹는 발열 원인일 수 있다. 렌더 최적화만으로는 S1이 다 풀리지 않을 수 있다는 뜻이다. 실제 모바일 값은 단계 0에서 잰다.
- B1. **봇 판단에서 큰 배열과 컬렉션을 새로 만든다.** `shortestPath`(`bot-navigation.ts`, 14곳에서 호출)가 호출마다 맵 크기 배열(`Int32Array`, `Uint16Array`)을 새로 할당한다. 판단 층이 전략(`bot-strategy.ts`), 전술(`bot-tactical.ts`), 즉시 안전(`bot-immediate-safety.ts`), 재배치(`bot-reposition.ts`), 피해(`bot-damage.ts`), 예약(`bot-director.ts`)으로 나뉘면서 `Set`/`Map`/`filter` 할당 지점도 늘었다.
- B1-a. **판단 일정.** `bot-scheduler.ts` 기준으로 전략 판단은 6틱마다 슬롯 번호로 분산되고(14봇이면 틱당 약 2~3봇), 전술 확인은 3틱마다 trail이 있거나 공격·귀환·도주·재배치 중인 봇만 한다. 특정 틱에 비용이 몰리는지는 측정으로 확인한다.
- B1-b. **점령 처리 추가 비용.** 점령이 일어날 때마다 `captureLosses`와 `recordBotCapture`(`bot-events.ts`)가 디버그 여부와 상관없이 실행된다. 작을 가능성이 높지만 계측 대상에 넣는다.
- B2. **`buildView`가 매번 큰 배열을 복사한다.** 연습 모드에서 틱마다(30Hz) `owners`, `trailMasks`, 참가자 객체를 통째로 복사한다.
- B3. **연습 모드는 시뮬레이션과 렌더링이 메인 스레드 하나에서 돈다.**

**HUD (S2)**

- H1. **HUD를 30Hz로 갱신한다.** `ui.updateView`가 30Hz로 돌면서 랭킹 비교 키를 `JSON.stringify`로 만든다. 순위나 점수가 바뀌면 랭킹 DOM을 통째로 다시 만든다.

**멀티·방장 (S4)**

- N1. **스냅샷 대부분이 칸 배열이다.** 48KB 대부분은 `owners`(base64 약 12.8KB)와 `trailMasks`(2바이트씩, base64 약 25.5KB)다. `trailMasks`는 거의 0인데 매번 전부 보낸다.
- N2. **인원수만큼 직렬화한다.** `publishSnapshot`이 받는 사람마다 객체를 새로 만들고, `lan-host.ts` `emit`이 그때마다 `JSON.stringify`를 다시 한다.
- N3. **방장 자기 화면도 직렬화를 거친다.** 같은 앱 안의 loopback인데도 문자열로 바꿨다가 다시 파싱하고 base64를 해제한다.
- N4. **네이티브로 넘길 때 한 번 더 변환된다.** 게스트에게 보내는 큰 문자열이 Capacitor 브리지를 지나면서 다시 바뀐다.
- N5. **base64 인코딩이 느리다.** `encodeBytes`가 글자 하나씩 문자열을 이어 붙인다.
- N6. **방장 루프가 너무 자주 깨어난다.** `pump`를 `setInterval(10ms)`로 돌린다. 틱은 33ms마다인데 초당 100번 깨어난다.
- N7. **방장은 시뮬레이션과 자기 화면 렌더링을 같은 메인 스레드에서 처리한다.**

## 2. 목표, 합격 기준, 비목표

### 2.1 측정 조건 (모든 비교에 공통)

- **기기:** S24+ (Android 15, 120Hz), S20+ (Android 13). 기록 항목은 모델, Android 버전, WebView(Chrome) 버전, APK 빌드 커밋.
- **환경:** 실내 온도, 시작 배터리 온도, 화면 밝기(고정값, 자동 밝기 끔), 충전 여부(측정 중 충전 안 함), 배터리 잔량, 절전 모드 꺼짐.
- **시작 조건:** 이전 측정이 끝나고 기기를 식힌다. 시작 배터리 온도는 직전 측정과 ±1℃ 안이어야 한다.
- **반복:** 시나리오마다 최소 2회. 두 번의 차이가 15%를 넘으면 3회째를 돌린다.
- **배터리 온도는 보조 지표다.** 판단은 프레임 시간, 렌더 횟수, 틱 비용 같은 직접 지표로 하고, 온도는 방향만 확인한다.

### 2.2 재현 시나리오

- **자동 플레이:** 고정 시드와 고정 봇 설정으로 사람 입력 없이 같은 경기를 재현한다. v0.4 기준으로 두 가지 방법이 있다.
  - **1안: 봇 관전 모드 재사용.** 이미 있는 `?debug=1&spectate=1`(14봇 전원)에 봇 따라가기 카메라를 켠다. 카메라와 줌은 실제 플레이와 같다(`cssZoom`이 따라가기 중이면 게임 줌을 쓴다). 추가로 필요한 것:
    - **디버그 수집기를 끄는 스위치.** 지금은 관전 모드가 `BotDebugCollector`와 결정 관찰기를 같이 켠다. 그대로 재면 계측값이 무거워지므로 `?metrics=1` 측정에서는 끈다.
    - **측정용 빌드.** 측정·실험 기능 전체의 활성화 조건은 **dev/test 빌드 또는 성능 측정 플래그가 켜진 APK**로 통일한다. 관전 모드는 지금 dev/test 빌드에서만 켜진다. 그런데 test 모드 APK는 번들 폰트(`MODE==='apk'`일 때만 로드)와 오프라인 폰트 플러그인(`vite.config.ts`)이 빠져서 배포 APK와 구성이 다르다. 그래서 **APK 모드는 그대로 두고, 측정 기능(관전, 계측, 수집기 끄기)만 별도 빌드 플래그(예: `VITE_PERF=1`)로 켠다.** 배포 빌드에는 이 플래그가 들어가지 않는다.
    - **외형과 설정 고정.** 연습 모드 `matchId`는 같은 시드여도 매번 난수 꼬리가 붙고(`practice.ts`), 봇 마커 배정은 그 `matchId`로 섞인다(`bot-cosmetics.ts`). 그래서 같은 경기를 반복해도 마커 종류와 애니메이션 부하가 달라진다. 측정 모드에서는 `matchId`를 시드와 판 번호로 만들고(예: `perf-<seed>-<판 번호>`), 색 스타일, 영토·점령 이펙트 설정, 따라갈 봇 슬롯, 해상도 배율도 고정해서 기록한다. 시뮬레이션은 `matchId` 값이 아니라 시드로 정해지지만, 고정해 두면 그 가정에 기대지 않아도 된다.
    - **한계.** 관전에서는 입력이 꺼지고, 내 점수 HUD, 리스폰, 벽 하이라이트, 예측선 경로가 빠진다. 빠진 작업의 비용은 관전 결과로는 알 수 없다.
  - **2안: 사람 자리를 봇 AI가 조종.** 방장 루프가 접속이 끊긴 사람을 봇 AI로 조종하는 경로(`room-loop.ts`, `getBotInputs`의 `selected`)를 연습 모드에 붙인다. HUD와 입력 경로까지 실제와 같다. 다만 지금 사람 자리는 귀환만 하는 모드(`returnOnly`)라서 전체 판단을 쓰려면 정체성(`createBotIdentity`) 생성이 필요하다.
  - **관전 시나리오는 반복 가능한 공통 부하 측정에 쓴다.** A′ 수동 플레이에서도 같은 구간별 계측을 하고, 관전에서 빠진 경로의 비용이 유의미하면(기준: A′의 해당 구간 합이 프레임당 CPU 시간의 10% 이상) 2안 시나리오를 추가한다.
- **시나리오 A′ (수동 플레이 계측):** 사람이 직접 연습 모드 1판(4분). 관전과 같은 계측을 켜고 같은 시드·고정 설정을 쓴다. 입력은 사람이라 반복 재현은 안 되므로 판정이 아니라 **관전에서 빠진 경로의 비용 확인**과 자동 플레이 대표성 확인에 쓴다. 최적화 전후에 각각 2회 측정한다.
- **시나리오 A (싱글 지속 부하):** 연습 모드 자동 플레이 3판 연속, 약 15분.
- **시나리오 B (설정창):** 연습 모드 3분 진행 → 설정창 열고 10초 → 진동 토글 1회 → 닫기를 5회 반복.
- **시나리오 C (LAN):** 4인 방, S24+ 방장, 1판.
  - **C-sim (보조):** 게스트 기기가 부족할 때 같은 앱의 테스트 게스트(메모리 채널)로 방장 부하를 재현한다. 직렬화량, 시뮬레이션 비용, 방장 렌더 비용 확인에만 쓴다. Capacitor 브리지, TCP 송신, Wi-Fi 무선 발열은 재현하지 못한다.
  - **C-real (합격 판정):** 실기기 LAN(같은 공유기 또는 핫스팟). 단계 4의 Gate는 C-real 결과로만 판정한다. 게스트 기기가 2대뿐이면 3인 방으로 측정하고 그 사실을 기록한다.
- **시나리오 D (메뉴 방치):** 메뉴 화면에 5분 둔다. 메뉴에서 생기는 소모를 확인한다.

### 2.3 목표 지표

| 지표 | 비교 대상 | 목표(제안) |
| --- | --- | --- |
| 실제 렌더 횟수/초 | — | 게임 중 60 (120Hz 기기 포함). 메뉴·설정창은 4장 정책대로 |
| 렌더 프레임 간격 p95 | — | 16.7ms × 1.2 = 20ms 이하 |
| 1% low (렌더 간격 기준) | — | 50fps 이상 |
| 프레임당 CPU 시간 p95 (Phaser step + render 전체) | 기준선 | S24+ 8ms 이하, S20+ 12ms 이하 |
| 초당 JS 작업 시간 (발열 지표) | 최적화 전 기준선 | 시나리오 A에서 40% 이상 감소. 120→60 상한만으로도 줄어드는 지표 |
| 틱 비용 평균·p95 | M2-b 기준선 | **v0.4: 수치는 단계 0 후 확정.** 봇 동결 시점 PC 평균이 이미 3.37ms라서 예전 목표(PC p95 4ms)는 행동을 바꾸지 않고는 어려울 수 있다. 행동 동일 제약 안에서 기준선 대비 평균 20% 이상, p95 30% 이상 감소를 잠정 목표로 둔다 |
| 모바일 초당 시뮬레이션 시간 | 최적화 전 기준선 | 시나리오 A에서 렌더 쪽 초당 작업 시간과 함께 보고, 단계 2/3 순서 판단에 쓴다 |
| 틱 비용 max | — | 33ms(틱 한 칸) 미만 |
| 지속 성능 | **같은 측정 안에서** 첫 3분 대비 마지막 3분 | 렌더 간격 p95 악화 10% 이내 |
| 최적화 효과 | **최적화 전 기준선** 대비 | 시나리오 A의 프레임당 CPU 시간 p95 30% 이상 감소 |
| 배터리 온도 상승폭 (보조) | 최적화 전 기준선 대비 | 상승폭이 줄어드는 방향이면 OK |
| 설정창 닫을 때 가장 긴 프레임 | 기준선 | 50ms 이하 |
| 방장 송신량, 1차 (delta 없음) | 기준선 1.44MB/s | 약 500KB/s 이하 (trail 목록화 + 직렬화 공유) |
| 방장 직렬화량, 1차 | 기준선 1.92MB/s | 약 170KB/s 이하 (본문 한 번 + loopback 직통) |
| 방장 송신량, 2차 (delta 도입 시) | 1차 결과 | 200KB/s 이하 |

1차 송신량 추정: `owners` 12.8KB + trail 목록 수 KB + 참가자·이벤트 수 KB ≈ 16KB × 3명 × 10Hz ≈ 480KB/s. 직렬화량은 본문 1회 × 10Hz ≈ 160KB/s. 단계 0에서 실제 크기로 고친다.

**잠정 수치:** 이 표의 수치(30%, 40%, 8/12ms, 아래 G1의 64MB 예산 등)는 모두 잠정이다. 단계 0 기준선이 나오면 확정하고, 바뀐 값과 이유를 `docs/performance-baseline.md`에 남긴다.

### 2.4 비목표

- 게임 규칙, 밸런스, 조작감은 바꾸지 않는다. 틱 30Hz, 스냅샷 10Hz, 맵 크기, 봇 판단 주기는 그대로 둔다.
- 맵을 줄이는 실험(친구방 작은 맵)은 별도로 진행한다.
- 보이는 모습은 바꾸지 않는다. 바뀌는 경우는 승인을 받는다.
- 엔진은 교체하지 않는다.

## 3. 진행 순서와 Gate

```
단계 0 계측 수정 + 기준선
  → 단계 1 프레임 상한 + 불필요한 갱신 제거
  → 재측정 (Gate 1)
  → [Gate 0에서 시뮬레이션 비중이 크면] 단계 3 C1~C2 먼저 (행동 동일 최적화)
  → 단계 2a RenderTexture 실험 (Gate 2a)
  → 단계 2b 렌더 본작업
  → 재측정 (Gate 2)
  → 단계 3 봇·시뮬레이션 판단 (Gate 3)
  → 단계 4 LAN 판단 (Gate 4)
  → 단계 5 정리
```

각 단계 끝에 기준선 대비 표를 `docs/performance-baseline.md`에 추가한다. 다음 단계로 넘어갈지는 Gate 기준으로 정한다.

## 4. 화면 상태 × 모드별 루프 정책 (Q2 설계 기준)

정책 대상:

- **렌더:** Phaser 그리기
- **시뮬레이션:** 연습 `PracticeSession` 또는 방장 `RoomLoop.pump`

- **수신 처리:** 스냅샷 → `setView` → `drawView`(청크 갱신) → HUD

규칙:

- **방장 시뮬레이션은 Phaser 루프에 넣지 않는다.** 지금처럼 타이머(`lan-host.ts` `pump`)로 돈다. Phaser를 재워도 방장 계산은 멈추지 않는다.
- **연습 루프를 Phaser `update`로 합치면** Phaser를 재울 때 연습 시뮬레이션도 같이 멈춘다. 설정창·결과 화면에서는 기존 동작과 같다. 그 밖의 상태에서 연습 시뮬레이션이 계속 돌아야 한다면 연습 루프를 합치지 않는다.
- **"렌더 정지"는 `game.loop.sleep()`만으로 끝나지 않는다.** 렌더를 재워도 스냅샷이 올 때마다 `setView → drawView`가 바로 불리기 때문이다.
- **보류하는 것은 화면 반영뿐이다.** 스냅샷 검증과 네트워크 상태 갱신은 계속 수행하고, `drawView` 및 게임 HUD 갱신만 최신 뷰 하나로 병합한다. 구체적으로:
  - **계속 즉시 처리:** 스냅샷 검증(`SnapshotGate`), 입력 확인 seq(`lastAppliedInputSeq`), `lifeId`·생존 상태 변화와 그에 따른 입력 활성화·리스폰 처리(`display()`의 상태 로직), 연결 상태, 보상 관찰(`rewards.observe`), 예측용 `Presentation.accept`(가벼움, 재개 시 끊김 방지).
  - **제어 이벤트 즉시 처리:** 결과(`match:result`), 방 상태(`room:view`), 오류·방 종료(`app:error`), 일시정지·재개(`room:paused`/`room:resumed`).
  - **병합:** `GameScene.drawView`(청크·아바타·이펙트 갱신), 게임 HUD(`ui.updateView`). 렌더가 재개되는 첫 프레임에 가장 최신 뷰로 한 번만 반영한다. 이때 영토 dirty 판정은 마지막으로 반영한 뷰와 비교하므로 중간 스냅샷의 변경도 빠지지 않는다.
  - 현재 `display()`는 상태 로직과 화면 반영이 섞여 있다. Q2에서 둘을 나누는 것부터 한다.
- 렌더를 다시 시작할 때 생기는 비용(U3)은 다음 프레임으로 나눠 처리한다.
- 정지 대신 프레임 수만 낮출지(예: 온라인 설정창에서 15fps)는 Gate 1에서 정한다.

## 5. 작업 단계

### 단계 0 (P0): 계측 수정과 기준선

**M1. 계측 수정 (가장 먼저)**

- frame meter를 Phaser 루프(`game.events` `prestep`/`poststep`/`prerender`/`postrender`)에 붙인다. 측정 항목:
  - 실제 렌더 횟수/초, 렌더 간격 p50/p95/max, 1% low
  - 별도 rAF 간격 (참고용, 화면 주사율 확인)
- **최상위 CPU 지표 (판정용):**
  - 프레임당 Phaser step CPU 시간 (`prestep` → `poststep`, scene `update` 포함)
  - 프레임당 Phaser **render** CPU 시간 (`prerender` → `postrender`). Graphics 삼각분해(R1)는 이 구간에 들어간다. 핵심 가설을 검증하는 지표다.
  - 프레임 밖 JS 시간: 스냅샷 수신 처리(`setView`/`drawView`), HUD, 연습 루프 등 Phaser 프레임 밖에서 도는 작업
  - **초당 JS 작업 시간** = 위 세 가지의 1초 합계. 발열 판단용이다. 120→60 상한은 프레임당 비용이 같아도 이 값을 줄인다.
- **원인 분석용 내부 구간:** `drawView`, 영토 이펙트, 점령 이펙트, 마커, 미니맵, 벽 하이라이트, HUD(`ui.updateView`). 고해상도 타이머로 링버퍼에 쌓는다.
  - 구간은 **중첩되지 않는 leaf 구간**으로만 정의한다. 상위 지표와 내부 구간을 더해서 합계를 내지 않는다(이중 계산 금지).
  - 상위 지표에서 내부 구간 합을 뺀 값을 "기타"로 표시해서 계측 누락을 드러낸다.
- GPU 시간은 브라우저에서 직접 재기 어렵다. 렌더 CPU 시간과 원격 디버깅 녹화의 GPU 트랙으로 보조 확인한다.
- 틱 비용을 쪼갠다: 봇 관찰, 봇 판단(판단 횟수 / 판단 1회 비용), `stepMatch`, 점령 처리, `buildView`.
  - 연습: `PracticeSession.advance`
  - 방장: `RoomLoop`
- GC 확인: 기기 녹화(Chrome 원격 디버깅 Performance)에서 GC 이벤트 수와 시간을 본다. 가능한 환경에서는 `performance.measureUserAgentSpecificMemory` 등 보조 지표를 쓴다.
- 스냅샷 계측:
  - LAN 경로에도 `snapshotBytes`를 누적하고, 직렬화량과 송신량을 따로 센다.
  - 크기를 재려고 다시 `JSON.stringify`하지 않는다. 이미 만든 문자열 길이를 쓴다.
  - 온라인 서버(`src/server/loop.ts`)의 이중 stringify도 같은 방식으로 고친다.
- 계측은 `?metrics=1`일 때만 켠다. 꺼져 있을 때 비용이 0에 가까운지 확인한다.

**M2. 자동 플레이 모드** (2.2 참고). 측정 빌드 플래그로 켠다. 관전 모드에 디버그 수집기 끄기 스위치, 재현 가능한 `matchId`, 따라갈 봇·색 스타일·이펙트 설정 고정 옵션을 추가하고, 실제로 쓴 값을 측정 결과에 함께 기록한다.

**M2-b. Node 틱 비용 기준선.** 봇 쪽 비용 측정 규약을 그대로 써서 PC(Node)의 틱 비용 p50/p95/max를 낸다. 봇 쪽은 평균만 기록했으므로 분포를 추가한다. 연습 구성(사람 1 + 봇 13)도 같이 잰다. 이 값은 브라우저·모바일 측정과 비교하는 기준이 된다.

**M3. 기록 스크립트.** 무선 adb로 30초마다 배터리 온도, 렌더 횟수, 틱 p95를 CSV로 남긴다. 계측 값은 페이지에서 꺼내 온다. 스크립트는 `.local/`에 둔다.

**M4. 기준선 측정.** 시나리오 A~D를 2.1 조건으로 측정한다. 원인 후보(R1, U1, B1, N2 등)마다 실제 비중을 표로 남긴다.

**산출물:** `docs/performance-baseline.md`

**Gate 0 (단계 1로 넘어가는 조건)**

- 계측이 실제 렌더 횟수와 rAF 횟수를 구분해서 보여준다.
- 자동 플레이 2회 반복 결과의 차이가 15% 이내다.
- 원인 후보별 비중 표가 있다. 비중이 거의 없는 후보는 이후 단계에서 **생략** 표시한다.
- **단계 2와 3의 순서 결정 (v0.4 추가, v0.4.1 수정).** 시나리오 A의 모바일 초당 JS 작업 시간에서 시뮬레이션과 렌더 쪽 비중을 비교한다.
  - **겹치지 않게 나눈다.** 연습 루프를 Phaser `update`에 합치면 시뮬레이션이 step 시간 안에 들어간다. 그래서 비교는 **틱 비용(시뮬레이션) vs 시뮬레이션을 뺀 나머지 step·render 비용**으로 한다. 전체 합계는 따로 그대로 보고한다.
  - **LAN 방장**은 별도 타이머로 도는 `RoomLoop`(시뮬레이션)과 스냅샷 직렬화·송신 비용도 합계와 비교에 넣는다.
  - 단계 1(프레임 상한)은 렌더 쪽만 줄이므로, 시뮬레이션 비중이 렌더와 비슷하거나 크면 Gate 1 뒤에 **단계 3(C1~C2)을 단계 2보다 먼저** 한다. C2는 행동을 바꾸지 않는 할당 제거라서 봇 동결과 충돌하지 않는다.

### 단계 1 (P0): 프레임 상한과 불필요한 갱신 제거

- **Q1. 60fps 상한.**
  - Phaser 설정에 `fps:{limit:60}`을 넣는다.
  - 연습·입력 루프를 합칠지는 4장 규칙을 따른다.
  - 네이티브 주사율 낮추기(Android `Surface.setFrameRate` 등)는 Gate 1 결과를 보고 정한다.
- **Q2. 4장 정책 구현.** 렌더 정지 + 수신 보관 + 재개 시 1회 반영.
- **Q3. 블러 제거(U1).** `backdrop-filter`를 빼고 반투명 배경만 남긴다. **승인 필요(D2).** Q2로 렌더가 멈추면 블러 비용도 크게 줄어든다. Q2 적용 후 측정해서 블러 비용이 무시할 만하면 블러를 **유지**한다.
- **Q4. 설정 변경 시 필요한 것만 갱신(U2).** `colorStyle`이 실제로 바뀔 때만 `refreshColors()`를 부른다.
- **Q5. 설정창 닫을 때 일 나누기(U3).**
- **Q6. 해상도 상한(R4).** 모바일(`pointer:coarse`)은 배율 최대 2로 시작한다. 1.5까지 낮출지는 측정과 화질 비교 스크린샷으로 정한다.
- **Q7. GPU 옵션.** `powerPreference`를 `'default'`로 바꿔 A/B 측정만 한다. 차이가 없으면 바꾸지 않는다.

**Gate 1**

- 게임 중 실제 렌더가 60/초인지 확인한다.
- 시나리오 B에서 설정창 닫을 때 가장 긴 프레임이 50ms 이하인지 본다.
- 시나리오 A에서 렌더 간격 p95가 20ms 이하이고, 첫 3분 대비 마지막 3분 악화가 10% 이내인지 본다.
  - **둘 다 만족하면:** 단계 2는 실험(2a)만 하고, 효과가 작으면 본작업(2b)은 생략할 수 있다.
  - **만족하지 못하고, 비중 표에서 영토 렌더(R1)가 상위면:** 단계 2a로 간다.
  - **틱 비용이 주원인이면:** 단계 3을 먼저 한다.

### 단계 2a (P0): RenderTexture 실험

먼저 실험 플래그(`?experimentTerritoryCache=1`)로만 구현한다. 이 플래그는 **dev/test 빌드 또는 성능 측정 플래그가 켜진 APK에서만** 활성화된다(측정 APK에서 기준선과 같은 조건으로 실험을 비교하기 위해). 배포 빌드에서는 무시한다.

**설계 조건**

- **굽는 대상:** 영토(채우기, 옆면, 외곽선)만 굽는다. trail은 자주 바뀌므로 지금처럼 Graphics로 남겨서 **분리**한다. 영토 위를 지나는 trail은 영토 레이어 위에 그린다. 그리는 순서가 지금과 같아야 한다.
- **텍스처 크기:** 청크 바운딩 박스 + 옆면(`lipDepth`) + 선 두께만큼 여유를 둔다. 청크 경계에서 잘리는 부분이 없게 한다.
- **메모리 예산:** 메모리 = Σ(텍스처 폭 × 높이 × 4바이트)이고, 해상도 배율이 축마다 곱해진다(배율 2면 면적 4배). 굽는 해상도는 화면 배율이 아니라 **월드 줌을 반영한 화면 픽셀 기준**으로 정한다. 전체 예산은 우선 64MB 이하로 잡고, 실험에서 실제 값을 잰다.
- **화면 밖 청크:** 화면 + 여유 2~4칸 안의 청크만 텍스처를 가진다. 여유 밖으로 일정 거리 이상 벗어난 청크는 텍스처를 해제한다(재생성 비용과 균형을 맞추는 여유를 둔다). 다시 들어오면 그때 굽는다.
- **재생성 조건:** 청크 안 소유권이 바뀔 때, 색 스타일이 바뀔 때, 이웃 청크의 옆면이 걸칠 때(지금 dirty 규칙 그대로), 컨텍스트를 잃었을 때.
- **한 프레임 예산:** 한 프레임에 다시 굽는 청크 수에 상한을 둔다(예: 2개). 대규모 점령으로 dirty가 몰리면 다음 프레임으로 나눈다. 그동안은 이전 텍스처를 보여준다.
- **처리 순서:** 화면 안에 보이는 dirty 청크를 먼저 굽고, 그다음 화면 여유 영역, 마지막으로 나머지를 굽는다. 같은 우선순위 안에서는 내 위치에 가까운 순서다.
- **최대 지연:** 화면에 보이는 청크는 소유권이 바뀐 뒤 **최대 100ms(60fps 기준 6프레임)** 안에 반영한다. 이 한도에 걸리면 그 프레임은 예산을 넘더라도 남은 화면 안 청크를 모두 굽는다.
  - 이 강제 굽기는 한 프레임에 일을 몰아서 끊김을 만들 수 있다. 그래서 대규모 점령 테스트에 반드시 포함하고, **지연(100ms)과 프레임 비용(가장 긴 프레임이 기준선보다 나빠지지 않음)을 동시에 만족해야 통과**다. 둘 중 하나라도 못 지키면 캐시를 억지로 통과시키지 않고 **실험 실패**로 판정한다.
- **빈 화면 금지:** 텍스처가 없는 청크가 화면에 들어오면 굽기 전까지 지금 방식(Graphics 직접 그리기)으로 그린다. 바닥만 보이는 프레임이 생기면 안 된다.
- **재생성 조건 (해상도 변경):** 굽는 해상도는 줌과 배율로 정해진다. 그래서 화면 회전·창 크기 변경, 카메라 줌 변경, `renderPixelRatio` 변경 때 모든 청크를 무효로 하고 위 우선순위대로 다시 굽는다. 다시 굽는 동안은 이전 텍스처를 늘려서 보여준다.

**측정 항목**

- 평상시 프레임당 step·render CPU 시간 (기준선 대비)
- 대규모 점령 직후 프레임 비용 (한 번에 수백 칸)
- 텍스처 메모리 합계
- 화면 이동 시 굽기 비용
- 청크 경계 잘림 여부 (스크린샷)
- WebGL 컨텍스트 손실 후 복구
- **화면 반영 지연:** 소유권 변경 시각과 해당 청크가 새 텍스처로 그려진 시각의 차이를 계측한다. 대규모 점령과 빠른 이동 상황에서 화면 안 청크의 최대 지연을 본다.
- **오래된 화면 검출 테스트:** 텍스처 결과와 같은 시점의 Graphics 직접 그리기 결과를 프레임마다 비교하는 테스트 모드. 다른 프레임이 연속으로 몇 개인지 센다. 스크린샷 한 장으로는 잡히지 않는 문제라서 필요하다.

**Gate 2a (본작업 진행 조건)**

- 평상시 프레임당 render CPU 시간이 30% 이상 줄어든다(잠정 수치).
- 대규모 점령 직후 가장 긴 프레임이 기준선보다 나빠지지 않는다.
- 메모리가 예산 안이다.
- 스크린샷이 기준선과 구분되지 않는다(경계 잘림 없음).
- 화면 안 청크의 반영 지연이 100ms를 넘지 않는다. 대규모 점령(강제 굽기 발생) 상황에서도 위 "가장 긴 프레임" 조건과 **동시에** 만족해야 한다.
- 새로 들어온 청크가 빈 화면으로 보이는 프레임이 0이다.
- 회전·줌 변경 직후에도 위 두 조건을 만족한다.

하나라도 실패하면 대안을 검토한다(칸마다 색을 입힌 Blitter 등). 그래도 이득이 작으면 G1을 **생략**하고 G2~G6만 진행한다.

### 단계 2b (P0/P1): 렌더 본작업

- **G1.** Gate 2a를 통과한 설계를 기본값으로 켠다.
- **G2. 컬링 여유 축소(R2).** 16칸을 2~4칸으로 줄인다. 영토, 영토 이펙트, 점령 이펙트 셋 다 적용한다. 빠르게 이동할 때 가장자리가 비지 않는지 확인한다.
- **G3. 매 프레임 작업 줄이기(R5).** 항목별 갱신 조건은 아래와 같다.
  - **벽 하이라이트:** 결과는 "내 위치 기준 반경 안의 경계선"이라 같은 칸 안에서도 바뀐다. 위치를 끊어서 판단하면 켜지고 꺼지는 시점이 지금과 달라지므로 쓰지 않는다.
    - 대신 매 프레임 **보여야 할 경계선 집합**만 계산한다(지금과 같은 거리 판정). 후보 경계선은 공간 격자로 미리 나눠 근처 몇 칸만 검사한다.
    - 그 집합(경계선 번호 목록)이 직전과 다를 때만 다시 그린다. 그림은 경계선 집합으로만 정해지므로 지금과 **완전히 같다**.
    - 그 밖에 `wallMargin`/`boundaryHighlight` 설정 변경, 생존 상태 변경, `phase` 변경, 맵 변경 때도 다시 그린다.
  - **예측선:** 바뀌는 조건은 다음 중 하나다. 내 이동 칸이 바뀜, 그 칸의 `owners` 변경, 그 칸의 내 trail 비트 변경, 내 생존 상태 변경, `phase` 변경, 내 색 변경. 하나도 해당하지 않으면 다시 그리지 않는다.
  - **나(self) 참가자 찾기:** 프레임마다 찾지 않고 스냅샷이 올 때 한 번 찾아 둔다.
  - **검증:** 갱신 조건을 끈 버전(매 프레임 다시 그리기)과 결과 그림이 같은지 테스트로 비교한다.
- **G4. 점령 이펙트 상한(R6).** 그리는 칸 수에 상한을 두고, 다시 그리는 빈도를 낮춘다. 보이는 모습이 바뀌므로 **승인 필요(D3)**.
- **G5. 마커 구성 단순화(R7).** 그림자·받침을 텍스처에 굽고, 펄스·이펙트는 나(self)와 애니메이션 마커에만 쓴다. 쓰지 않는 `mk:` 텍스처는 정리한다. **승인 필요(D3)**.
- **G6. HUD 갱신 빈도 낮추기(H1).** 같은 값이면 DOM에 다시 쓰지 않는다. 랭킹은 4~5Hz로 갱신하고 행을 재사용한다.

**Gate 2:** 2.3의 렌더 지표를 만족하면 단계 3으로 간다. 이때 시나리오 A의 남은 비용 중 틱 비용 비중이 작으면 단계 3은 C2(배열 재사용)만 하고 나머지는 생략한다.

### 단계 3 (P0/P1): 시뮬레이션과 봇

**봇 동결 제약 (v0.4):** 봇 기능은 `cb15860`에서 동결됐고, 봇 행동 변경은 이 PRD 이후로 미뤄졌다(`docs/bot-ai-freeze.md`). 그래서 단계 3은 **행동이 바이트 단위로 같은 최적화만** 한다. 아래 검증을 통과하지 못하는 변경은 이 PRD에서 하지 않고 동결 해제 후 봇 로드맵으로 넘긴다.

- **C1. 틱 비용 분석(P0).** 단계 0 계측으로 비용을 나눈다: 봇 관찰(`observeBotForTick`), 판단 층별(전략·전술·즉시 안전·재배치·피해·예약), `stepMatch`, 점령(`captureLosses`·`recordBotCapture` 포함), `buildView`. 층별 판단 횟수와 1회 비용을 함께 남긴다.
- **C2. 봇 작업 배열 재사용(P0, B1).** `shortestPath` 등 탐색용 배열을 맵마다 한 번만 만들어 재사용한다(`plannedCaptureWork`와 같은 방식). 맵 전체를 도는 `filter`도 줄인다. 주의할 점:
  - **순회 순서를 바꾸지 않는다.** `Set`/`Map`을 배열이나 비트맵으로 바꾸면 순회 순서가 달라져 동점 처리가 바뀔 수 있다. 순서가 결과에 쓰이는 곳은 기존 순서를 유지한다.
  - **난수 소비를 바꾸지 않는다.** 봇마다 시드 난수 스트림(행동, 특성, 예약, 일정)이 따로 있다. 호출 횟수나 순서가 바뀌면 이후 행동이 전부 달라진다.
- **C3. p95 원인 확인 (가설).** "판단 틱에 비용이 몰린다"는 가설을 아래 세 가지로 나눠 확인한다.
  - (a) 한 틱에 판단하는 봇 수: `bot-scheduler.ts`의 전략(6틱, 슬롯 분산)과 전술(3틱, 조건부) 일정이 실제로 고르게 나뉘는지
  - (b) 판단 1회 비용의 분포
  - (c) 판단 틱과 GC가 겹치는 정도
  - 결과에 따라 대응한다. (b)면 판단 1회 비용 자체를 줄이고(C2 확장, 캐시), (c)면 C2를 더 넓힌다. (a)의 분산 보정과 판단 분할은 판단 시점을 바꾸므로 **봇 동결 때문에 이 PRD에서는 하지 않는다.** 측정 결과만 남겨 동결 해제 후 봇 로드맵으로 넘긴다.
  - **C3도 아래 틱별 동일성 검증을 적용한다.** **기존 판단 틱까지 계산을 완료하고 동일한 결과를 적용할 수 있는 방식만 허용한다.** 유지할 수 없는 변경은 **행동 변경**으로 보고 동결 해제 후 승인 대상으로 넘긴다.
- **C4. `buildView` 배열 재사용(P1, B2).** 바뀐 칸 목록을 넘기거나 버퍼 두 개를 번갈아 쓴다. 렌더러가 `lastOwners`와 비교하는 방식은 유지한다.
- **C5. 연습 시뮬레이션을 Web Worker로(P1, B3).** C2~C4 이후에도 틱 max가 33ms를 넘거나, 틱 때문에 렌더 간격 p95가 목표를 넘으면 진행한다. **승인 필요(D4)**.

**봇·시뮬레이션 검증 (C2, C3, C4 공통)**

- **봇 쪽 궤적 해시 방식을 재사용하되, 성능 검증용 도구로 확장한다.** `scripts/bot-nickname-trajectories.ts`는 봇 동결 때 쓴 방식으로, 14봇 × 8시드(4, 19, 73, 11, 31, 47, 101, 137) × 3,600틱 동안 틱마다 입력, `owners`, `trailMasks`, 참가자 생명·위치·방향·입력 seq를 해시에 넣는다.
  - 그대로 쓸 수는 없다. 이 스크립트는 행동을 비교하기 **전에** 봇 소스 파일 해시가 동결본과 같은지 검사(12행)하므로, C2처럼 소스를 고치면 행동 비교까지 가지 못한다.
  - 새 스크립트(예: `scripts/perf-trajectory-equivalence.ts`)를 만든다. **소스 해시는 기록용으로 남기고, 행동 동일성(궤적 해시 일치)을 합격 기준으로 삼는다.**
  - 기준 궤적 파일과 결과 출력 경로를 인자로 받는다. 동결 증거(`evidence/bot-freeze-final/`, `evidence/bot-inner-anchor-adoption/`)는 읽기만 하고 덮어쓰지 않는다.
  - **기준선도 새 도구로 만든다.** 새 도구는 기존 도구보다 많은 항목(이벤트, 봇 메모리, 난수 상태, 중간 체크포인트)을 해시에 넣으므로, 기존 동결 증거의 해시와는 행동이 같아도 값이 다르다. 그래서 **동결 커밋 `cb15860`과 최적화 후보를 같은 새 도구·같은 해시 형식으로 각각 실행해 비교한다.**
    - 확장 기준선은 별도 경로(예: `evidence/perf-trajectory-baseline/`)에 새로 만들고, 만든 커밋과 도구 버전을 함께 기록한다.
    - 도구 자체가 맞는지 확인하는 장치: 새 도구가 기존 항목만 해시하는 호환 모드로 `cb15860`을 돌렸을 때 기존 동결 증거의 해시와 같아야 한다.
  - 최적화 전후(같은 새 도구 기준) 최종 해시와 모든 체크포인트가 같아야 한다.
- 이 PRD에서 추가하는 것:
  - **틱별 체크포인트.** 최종 해시만 다르면 어디서 갈라졌는지 모른다. 일정 간격(예: 30틱)마다 중간 해시를 남겨 처음 갈라진 틱을 찾는다.
  - **이벤트와 봇 메모리.** 그 틱의 이벤트 목록, 봇 메모리의 목표(`goal`)·다음 판단 틱·난수 상태도 해시에 넣는다.
  - **연습 구성.** 사람 1 + 봇 13 구성(사람 입력은 고정 스크립트)도 같은 방식으로 비교한다.
  - **사망 수.** 봇 쪽 도구처럼 시드별 총 사망 수도 같아야 한다.
- 한 틱이라도 다르면 실패다. 결과가 바뀌면 그건 동결된 봇 행동의 변경이다.
- 기존 봇 테스트 전체(동결 시점 일반 689개 통과, 기대 실패 8개)도 그대로 통과해야 한다.

**틱 비용 측정 규약:** 봇 쪽 규약(`evidence/bot-inner-anchor-adoption/cost.json` method)을 그대로 쓴다. 관찰기 없음, 120초, 8시드 × 3라운드, AB/BA 순서 교차, 팔(arm)마다 seed19 워밍업 1회 제외, 측정 전후 외부 Vitest/Playwright 실행 여부를 확인해 겹친 행은 제외. 결과는 라운드 중앙값과 시드별 중앙값으로 낸다. 여기에 p95/max를 추가한다.

**봇 작업과의 관계:** 봇 브랜치는 이미 master에 병합됐다(`fed55ee`). 남은 봇 과제(먼 피해 대응, 연결 단절 중립화 기억, HOME_CAPTURE 예측 등)는 동결 기록으로 보존돼 있고 이 PRD 이후에 진행한다. 이 PRD가 봇 파일을 고치므로, 동결 해제 후 봇 작업은 이 PRD의 최종 커밋을 기준으로 시작한다.

**Gate 3:** 틱 p95와 max가 2.3 목표를 만족하면 C4, C5는 생략한다.

### 단계 4 (P1): 멀티와 방장 부담

싱글 최적화가 끝난 뒤 진행한다. 프로토콜이 바뀌므로 서버, LAN, 클라이언트를 함께 바꾸고 `PROTOCOL_VERSION`을 올린다.

**1차 (delta 없음, 목표: 송신량 약 500KB/s, 직렬화량 약 170KB/s)**

- **N-a. 한 번만 직렬화(N2).** 사람마다 다른 값(`selfParticipantId`, `lastAppliedInputSeq`)을 본문에서 뺀다.
  - **한 프레임으로 결합 (유일안).** 공통 본문은 한 번만 `JSON.stringify`한다. 사람마다 프레임 문자열을 `{"k":"evt","e":"match:snapshot","h":{머리},"d":` + 본문 + `}`처럼 이어 붙여 만든다. 머리와 본문이 항상 같은 프레임에 들어가므로 묶기 규칙이 필요 없다. 지금의 `replaceKey`(꼬리 프레임 교체) 동작도 그대로 유효하다. 문자열 결합 비용과 프레임 크기는 측정한다.
  - **머리와 본문을 두 메시지로 나누지 않는다.** 네이티브 큐(`LanSocketPlugin` `enqueue`)는 같은 `replaceKey`의 꼬리 프레임을 교체한다. 그래서 머리가 아직 큐에 있을 때 본문이 머리를 덮어쓴다. 나누려면 쌍 전체를 한 단위로 교체하는 별도 큐 설계가 필요하고, 그건 이 PRD 범위 밖이다.
  - 프로토콜이 바뀌므로 `SnapshotGate`와 온라인 경로(socket.io)에도 같은 형식을 적용한다.
- **N-b. 방장 자기 화면 직통(N3).** loopback은 직렬화하지 않고 `MatchView`를 바로 넘긴다. 다른 사람이 바꿀 수 없도록 복사본이나 읽기 전용 규약을 둔다.
- **N-c1. trail 목록화(N1).** `trailMasks`는 0이 아닌 칸만 `[칸, 마스크]` 목록으로 보낸다.
- **N-d. base64 인코딩 개선(N5).**
- **N-e. 방장 루프 주기(N6).** 다음 틱 시각에 맞춰 `setTimeout`으로 깨운다.
- **N-f. 브리지 비용 측정(N4).** 비용이 크면 플러그인에 `broadcast` API를 추가한다.

**Gate 4-1 (C-real로만 판정):** 방장 기기의 렌더·틱 지표가 싱글과 비슷한 수준이고 발열 차이가 작으면 2차를 **생략**한다. C-sim 결과는 원인 분석에만 쓰고 이 판정에는 쓰지 않는다.

**2차 (delta, 목표: 송신량 200KB/s 이하), 승인 필요(D5)**

- **N-c2.** `owners`는 바뀐 칸만 보내고(delta), N틱마다 전체를 다시 보낸다(키프레임).
- 기준 스냅샷 번호(baseline seq), 버리는 메시지(`replaceKey`)와의 관계, 재접속·패킷 손실 때 다시 맞추기(resync) 규칙을 설계한다. LAN PRD v2의 "delta 없음" 결정을 바꾸는 것이다.

**3차 (P2)**

- **N-g.** 방장 시뮬레이션을 Worker로 옮긴다.

### 단계 5 (P2): 정리

- 남은 requestAnimationFrame 루프를 정리한다.
- 10판 연속 플레이 후 힙 스냅샷을 비교한다(이벤트 Set, 텍스처, 마커 이미지가 쌓이지 않는지).
- (선택) "절전 모드" 설정을 추가한다(30fps + 배율 1.5). **승인 필요(D7)**.

## 8. 위험

- **계측 오버헤드:** 계측이 측정값을 바꿀 수 있다. `?metrics=1`을 꺼 둔 빌드로도 렌더 횟수와 온도를 한 번 비교한다.
- **자동 플레이의 대표성:** 봇 조종은 사람의 움직임과 다르다. 대표성 확인용으로 사람이 직접 플레이한 측정도 1회 남긴다.
- **RenderTexture 메모리:** 고배율 기기에서 메모리가 커지면 WebGL 컨텍스트가 끊길 수 있다. 예산과 해제 규칙으로 막고, 컨텍스트 손실 복구를 테스트한다.
- **60fps 상한 체감:** 120Hz 기기에서 화면 이동이 덜 부드럽다고 느낄 수 있다. 직접 플레이해 보고 판단한다.
- **렌더 정지 후 재개:** 보관해 둔 최신 뷰 반영이 빠지면 화면이 어긋난다. 4장 상태 전환마다 테스트한다.
- **봇 최적화의 결과 변화:** 틱별 비교 테스트로 막는다.
- **delta 동기화:** 키프레임과 다시 맞추기 규칙을 검증해야 한다.
- **봇 동결과의 충돌:** 단계 3은 동결된 봇 파일을 고친다. 궤적 해시가 하나라도 다르면 되돌린다. 동결 해제 후 봇 작업은 이 PRD의 최종 커밋을 기준으로 시작해야 한다.
- **틱 비용 목표 미달:** 행동을 바꾸지 않는 최적화만으로는 시뮬레이션 비용을 충분히 못 줄일 수 있다. 그 경우 Worker 이전(D4) 또는 동결 해제 후 봇 쪽 비용 감축 과제로 넘긴다.
